# Работа четырёх участниц в коде

Распределение согласуется 9 ноября 2026 года. Имена участниц ещё не указаны, поэтому используются роли. Ядро версии 0.1.0, импорт и один цикл перепланирования подготовлены с ChatGPT/Codex. Это исходная работа, а не личные результаты участниц. Ниже сохранён план распределения с обновлениями по фактически выполненным частям. Статусы от 10 ноября имеют приоритет над первоначальными назначениями; планируемый файл не означает уже готовый модуль.

## Общее основание

Все начинают с examples/r03.json, срока приёмки 328 ч и возврата до 492 ч. Суда, поступления и ограничения условные. Для контроля есть examples/r03.reference.json: 1650 т у обоих методов, 6/5 рейсов, последняя приёмка 276/224 ч. Неизвестная фактическая величина не становится нулём. Единицы: целые часы от общего T0 и целые тонны.

Существующие общие API: planning.compare, planning.ready, planning.optimize, validation.check_schedule, validation.snapshot, replanning.replan, economics.compare_cost. Изначально каждая добавляет отдельный модуль и свой тестовый файл. Для временной недоступности судна разработчица расширяет domain.py и planning.py, интегратор отдельно расширяет независимую validation.py. CLI меняет интегратор после подключения модулей. Так общие файлы имеют одного владельца изменений.

## Приоритет до сдачи: три разных вида адаптации

Уточнение по скриншотам рекомендаций от 9 ноября: это план подготовки, не новый официальный регламент чемпионата. Для демонстрации приоритетны три **отдельных** опыта от одного R03, каждый с объявлением в 60 ч:

| Опыт | Новая информация | Статус кода |
|---|---|---|
| A1 | Второе поступление 825 т переносится 120→168 ч | Один цикл уже реализован и технически проверен |
| A2 | SIM-A недоступно на [120,200) ч | Реализовано 10 ноября: событие, планировщик, независимая проверка; 1650/1650 т, 6/5 рейсов, приёмка 280/264 ч |
| A3 | Предел партии 200 т на [120,168), затем исходный предел | Статический календарь есть, обновление после сообщения ещё не реализовано |

Условия каждого опыта сценарные. Они не складываются в один тяжёлый случай. Срок 328 ч, объём 1650 т и ресурсы исходного R03 сохраняются. Последовательность двух задержек переносится на следующий этап после трёх разных опытов. Для каждого нужны исходный план, обновлённый план, фиксированные решения, журнал новой информации и численные показатели.

Запуск и один цикл адаптации проверены ассистентом, а не всеми участницами лично. Каждая должна самостоятельно повторить вход→запуск→расписание и зафиксировать свой результат. Паспорт имеется в черновике, презентация в этой работе не создана.

## 1. Разработка: обработка разных обновлений

**Обновление 10 ноября:** A1 и A2 уже работают через существующий
`run_replanning`. После интеграции PR №1 файл `online.py` сохраняет API участницы
как совместимые входы к общей реализации. A2 реализован
ассистентом по запросу руководительницы; пример события —
`examples/vessel_unavailable.json`, описание — [здесь](vessel-unavailability.md).
Следующая новая часть разработчицы — A3 совместно с календарём условий.
Многократные сообщения остаются после этого; исходный план ниже сохранён
для понимания распределения, а готовые механизмы используются повторно.

**Новый модуль:** src/yana_planner/online.py. **Тесты:** tests/test_online.py. Ветка feature/online-events.

Планируемая функция:

```python
def run_online(cfg, events, deadline, *, time_limit=3) -> dict:
    ...
```

Сначала обобщить один шаг обновления для A1/A2/A3. Формат A1 прежний: type=arrival_delay, announced_at_h, arrival_index, new_arrival_h. Для A3 использовать records и build_conditions второй участницы. Для A2 согласованный новый формат: type=vessel_unavailable, announced_at_h=60, vessel_id=SIM-A, from_h=120, to_h=200.

Для A2 поле unavailable_intervals, проверка его формата, исключение рейсов по полному обороту, событие vessel_unavailable и независимая проверка уже реализованы. available_h сохраняется; конфликт с начатым рейсом возвращает requires_intervention. Использовать эти механизмы при дальнейшей интеграции.

Для сегодняшней приёмки run_online может принимать список из одного события: три отдельных запуска демонстрируют три механизма. После их завершения — расширение на два события (в 60 ч 120→168 ч, в 100 ч 168→192 ч); оно не должно отнимать время у A2/A3.

При каждом шаге фиксируются все отправления, начатые к этому моменту, включая отправления, назначенные после предыдущего обновления. Новый вызов получает обновлённый вход предыдущего шага и его полный план. Начальный план видит только исходные 0/120 ч, а не даты 168/192 ч. Обоим методам события раскрываются одновременно, каждый сохраняет собственную выполненную историю. Входные объекты не мутировать.

**Выход:** исходное сравнение, журнал шагов (момент, известный вход, снимки запасов, фиксированные рейсы, новые планы, статусы проверки), итоговые показатели обоих методов. При невозможности исполнения — явный статус, не фиктивные подтверждённые тонны.

**Приёмка сегодня:** три типа событий по отдельности; ни одного нового отправления задним числом; все начатые рейсы неизменны; балансы и расписания проходят check_schedule; тест доказывает отсутствие знания будущего у начального планировщика. Для A2 — проверка границ недоступности и невозможности незаметно изменить прошлую загрузку. Рост доставки не является условием сдачи.

## 2. Гидрология и ограничения: единый преобразователь условий

**Новый модуль:** src/yana_planner/conditions.py. **Тесты:** tests/test_conditions.py. Ветка feature/condition-calendar.

Планируемая функция:

```python
def build_conditions(cfg, records, *, at_h) -> dict:
    ...
```

Функция возвращает копию cfg с payload_calendar и closures в уже поддерживаемом формате. Она не запускает MILP и не заменяет независимую проверку рейсов.

Запись условия:

```json
{"kind":"payload_limit","announced_at_h":0,"from_h":120,"to_h":168,"max_t":200,"status":"scenario_assumption"}
```

Для kind=closure поле max_t отсутствует. На момент at_h применяются только записи с announced_at_h <= at_h. В первом варианте принимаются заранее объявленные условия: announced_at_h <= from_h, конечные интервалы [from_h,to_h), from_h < to_h. Поздние сообщения о ранее начавшихся ограничениях требуют отдельного расширения и сегодня явно отклоняются.

Нужно построить кусочно-постоянный календарь: при пересечении ограничений действует минимальный предел, после окончания восстанавливается исходное ограничение cfg, а не произвольно 400 т. Пересекающиеся/смежные интервалы остановок объединяются. Остановка распространяется на оба плеча движения по текущей модели. Связь «уровень — осадка — тонны» не выдумывается.

**Первый результат сегодня:** подготовить A3 с announced_at_h=60, from_h=120, to_h=168 и max_t=200. До 60 ч build_conditions не должен раскрывать новый предел, после объявления должен корректно передать календарь разработчице. Отдельно проверить статические предел 200 т на [120,168), остановку [40,48) и остановку [80,96) на исходном R03. Сначала проверить старые планы, затем получить новые через ready/optimize и повторно проверить. Статические тесты можно делать без ожидания первой участницы; они не выдаются за демонстрацию неожиданного обновления.

**Выход:** адаптер, таблица/JSON условий, три сравнения, конкретные нарушения исходных рейсов. **Приёмка:** границы интервалов, восстановление исходного предела, пересечение двух ограничений, фильтрация ещё неизвестного события, проверка гружёного плеча и возврата. Все операционные числа остаются сценарными.

## 3. Экономика: сетка ставок и порог выгоды

**Новый модуль:** src/yana_planner/sensitivity.py. **Тесты:** tests/test_sensitivity.py. Ветка feature/cost-sensitivity.

Планируемые функции:

```python
def run_cost_grid(cfg, baseline, alternative, deadline, base_terms,
                  *, x_parameter, x_values, y_parameter, y_values) -> list[dict]:
    ...

def break_even(cfg, baseline, alternative, deadline, base_terms,
               *, parameter) -> dict:
    ...
```

Повторно использовать economics.compare_cost. Выбрать и раскрыть две оси из separate_trip_operations_rub, active_vessel_hour_rub, waiting_vessel_hour_rub: по три уровня на каждую, остальные условия фиксированы. base_terms содержит billing_mode и общий horizon_h. Состав ставок не должен дублировать расходы. Существующая схема all_available_time оплачивает весь доступный ресурс на общем горизонте; её не выдавать за реальный договор.

На R03/328 у двух планов равный объём 1650 т. В условном горизонте 492 ч доступно 936 судно·ч; активная занятость 510/404. Оплата остальных часов применяется только при явно выбранной схеме, не как факт.

**Выход:** девять строк с исходными ставками, расходами двух методов, разницей и статусом; порог одной выбранной ставки, при котором разница меняет знак. Если коэффициент этой ставки в разнице равен нулю, вернуть «порог отсутствует», а не делить на ноль. Если не хватает исходных ставок — null/явный статус. Отрицательный математический корень не объявлять допустимым неотрицательным тарифом.

**Приёмка:** девять сочетаний, исходные объекты неизменны, явный ноль сохраняется, неизвестное не заменяется нулём, разные доставленные объёмы отклоняются, граница проверена подстановкой значений с обеих сторон. НМЦ не прибавляется к себестоимости. Диапазоны выбирает участница с объяснением, фактическая экономия не заявляется.

## 4. Руководительница/интегратор: проверка результата и общий эксперимент

Сводка дополнительно учитывает компромисс по средневзвешенной приёмке.
[Инструкция и объяснение](integrator-first-step.md). Руководительница 10 ноября самостоятельно повторила одиночное перепланирование
R03/328; вывод и JSON проверены, см. [протокол](integrator-run-log.md).
Независимая проверка недоступности добавлена 10 ноября: 41 тест проверки
исполнения и 90 тестов проекта прошли. Затем подключены интервалы к планировщику и событию недоступности:
A2 завершён как сценарная демонстрация, 104 теста прошли. Новый результат:
1650/1650 т, 6/5 рейсов, последняя приёмка 280/264 ч. Подключение A3 и
экономических модулей остальных участниц остаётся следующей работой.

**Твоя инженерная часть. Новый модуль:** src/yana_planner/experiments.py. **Тесты:** tests/test_experiments.py. Ветка feature/experiment-summary.

Планируемая функция:

```python
def summarize_experiment(result) -> list[dict]:
    ...
```

Вход — уже существующий JSON от compare или run_replanning. Для статического результата вернуть одну строку пары; для перепланирования — отдельные строки «до» и «после». Поля: phase, deadline_h, READY_status, MILP_status, READY_t, MILP_t, delta_t, READY_trips, MILP_trips, READY_last_receipt_h, MILP_last_receipt_h, equal_volume, trips_saved, hours_saved, tradeoff, actual_savings_rub.

Разницы рейсов и времени как улучшение показывать только при двух допустимых планах с одинаковым объёмом. При недопустимости/неизвестном результате производные разницы отсутствуют, а не равны нулю. Положительные trips_saved/hours_saved означают преимущество MILP. Если рейсов меньше, а окончание позже, tradeoff=true. actual_savings_rub остаётся null. Тоннаж сравнивается только при двух допустимых результатах; сам по себе частичный объём не обозначается выполненным заданием.

**Можно начать сейчас:** лично запустить контрольный R03 и готовый одиночный replan, прочитать сохранённый JSON и написать сводку без ожидания остальных. Контроль: исходно 1650/1650 т, 6/5 рейсов, 276/224 ч; при переносе 120→168 ч в проверенном запуске — 1650/1650 т, 6/5 рейсов, 284/272 ч. Другой допустимый MILP-план при лимите времени не считать ошибкой только за несовпадение времени: учитывать его статус.

Для A2 дополнить validation.py независимой проверкой unavailable_intervals по полному обороту судна. Проверить оборот, заканчивающийся ровно в from_h, начинающийся ровно в to_h и пересекающий интервал на один час. Не импортировать проверку кандидатов из planning.py: это должна оставаться отдельная проверка исполнения. Единый итог по A1/A2/A3 собирается только после фактического запуска, значения A2/A3 заранее не заполнять.

**Приёмка:** тест равного объёма, тест разных объёмов, тест отсутствующего/недопустимого результата, тест компромисса «меньше рейсов, позже конец». Сверить хотя бы один баланс вручную по журналу событий. Затем подключить новые модули участниц и перенести в паспорт только реально выполненные расчёты с их версиями входов.

## Совместная работа и сдача

Каждая сдаёт свой модуль, свой файл тестов, пример входа и результата, короткое объяснение выбранного метода и ограничений. Это план задач, а не заявление о написанном участницами коде. Вклад ИИ и личные действия фиксировать отдельно.

Команды проверки:

```sh
python -m unittest discover -s tests -v
ruff check src tests
ruff format --check src tests
```

Новые зависимости и общие поля сначала согласуются. Общие модули и CLI объединяет интегратор после проверки контрактов. Тесты должны проверять поведение и границы, а не повторять реализацию строка в строку.

Репозиторий опубликован с закрытым доступом: [EvalenkoEkaterina/yana-planner](https://github.com/EvalenkoEkaterina/yana-planner). Приглашения выдаёт владелица по GitHub-логинам, участницы принимают их в своих аккаунтах. Состояние автоматических проверок доступно в [Actions](https://github.com/EvalenkoEkaterina/yana-planner/actions). Для закрытых сведений предусмотрена игнорируемая private_data/.
