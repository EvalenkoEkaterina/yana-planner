## Схема

1. Каталог направлений и реестр источников над формой.
2. Условия поставки.
3. Выбор стратегии; включение стоимости; общий горизонт и явная схема оплаты.
4. Карточки судов: сохранены скорость погрузки, подготовка до погрузки и подготовка после возврата; добавлены три тарифа, происхождение и источник для каждого судна.
5. Поступления и одиночное событие задержки / погодного запрета.
6. Сводка, проверка/выгрузка JSON; запуск только поддерживаемых сервером возможностей.
7. Результат: прежнее расписание/статусы + общая стоимость, составляющие и per_vessel. Без стоимости показывается «не рассчитано», не 0. Разность показывается только при equal_volume=true.

## Предложение подключения, требует согласования

Это не существующий HTTP API. Сервер сейчас принимает старую форму. До интеграции dispatcher.js блокирует запуск с новыми настройками и позволяет скачать пакет. Не выставлять capabilities до реальной поддержки.

После подключения интегратор может передать в render_template('index.html'):

```python
dispatcher_capabilities={
    'route_packages': True,
    'economics': True,
    'weather': True,
    'loading_rate': True,
}
```

В обычный POST формы добавлено поле `route_package_json` — JSON envelope `yana-route/1`, наполняется перед submit, когда capabilities объявлены. Проверять его сервером через `import_route_package`, затем передавать scenario/deadline/strategy/cost_terms/event в штатный путь расчёта и web_worker с общим timeout. Не доверять браузерной валидации. Не обрабатывать route_package как неявный R03; сохранять маршрут, входы, событие, тарифы, источники и версию кода в истории.

Канонические поля внутри envelope соответствуют договорам: strategy='trips'/'cost'; cost_terms.billing_mode/currency/horizon_h/vessel_rates[ID]; weather_closure с announced_at_h, closures, rule_status, data_kind, source, forecast_issued_at; load_rate_tph, load_setup_h и prep_h в судне.

Сначала интегрировать существующий транспортный объект, потом новые цели и event. Если часть возможностей ещё не подключена, не объявлять её True. Смешение двух событий в одном пакете отклоняется. Вариант v1 требует T0 с явным смещением для прогноза; поддержка отдельного IANA timezone может быть расширена согласованно.

Шаблон результата читает `run.result.costs.planner`, `costs.equal_volume`, `costs.scenario_difference_rub`, `planning_strategy`. Это существующий формат compare/run_replanning из ветки коллеги. Сохранённые входы читают cost_terms из inputs либо результата. Статусы: scenario_cost, missing_cost_inputs, отсутствие результата. Никаких демонстрационных сумм в живой результат не подставляется.

До подключения в старой ветке расчёт по скорости и денежная цель не запускаются. CLI-скрипт также явно отказывает для неподдерживаемых возможностей, а не подменяет денежную цель минимумом рейсов. Старое ядро может оценить готовый план с равными индивидуальными ставками через явное преобразование к старому общему формату. Разные ставки требуют нового ядра.

## Проверка объединения

- Старые R03/задержка и восстановление примеров продолжают работать.
- Данные по скорости и обоим видам подготовки не теряются при ошибке/сохранении.
- Изменения маршрута реально меняют scenario, название в истории и сохранённые условия.
- cost действительно достигает денежной цели; пример economic-choice из ветки коллеги выбирает ожидаемое судно.
- Погодное событие передаётся без знания будущего в первоначальном плане; конфликт начатого рейса виден как requires_intervention.
- Пустой тариф не ноль, явный ноль сохранён; documented без source отклоняется; разные ID отклоняются.
- Одинаковый горизонт оплаты до/после и у обоих методов; расходы не сравниваются как экономия при разном объёме.
- После ошибки POST восстановить все новые поля или восстановить валидированный envelope, а не только прежние поля. Это работа серверной интеграции.

Статический снимок static/data/batagay.snapshot.json соответствует reports/averkieva/batagay/snapshot.json. Он подписан как сохранённый учебный расчёт и не является ответом на изменённые условия формы.
