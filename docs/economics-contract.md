# Экономическая часть: первый рабочий шаг

Статус: расчёт стоимости готового допустимого расписания по индивидуальным
ставкам судов и экономическая стратегия MILP работают в ядре и CLI.
Подключение полей к сайту — следующий шаг. Схема оплаты согласована с
экономистом команды 13 ноября как сценарное допущение. Применимость
к реальному договору требует подтверждения оператором; реальные ставки ещё ожидаются.

## Выбор стратегии в ядре

Функции `planning.optimize` и `planning.compare` принимают параметры
`strategy="trips"` (по умолчанию) или `strategy="cost"`, а также `cost_terms`.

| Стратегия | Последовательные цели |
| --- | --- |
| trips | Максимум принятого объёма, затем минимум рейсов, затем последняя приёмка |
| cost | Максимум принятого объёма, затем минимум сценарной стоимости, затем последняя приёмка |

Дешёвая недопоставка не может победить больший объём. Если оптимальность поиска
не подтверждена по всем этапам, результат не выдаётся за доказанный глобальный
оптимум. Автоматические повторы используют приоритеты выбранной стратегии и
сохраняют лучший проверенный план, даже если он содержит больше рейсов.

По экономической стратегии два дешёвых рейса могут победить один дорогой.
При равной стоимости третья цель выбирает более раннюю приёмку, а не меньше
рейсов. Количество рейсов всё равно выводится как характеристика результата.

Стоимость раскладывается на постоянную оплату доступности всего флота и
вклад выбранных рейсов. Для кандидата рейса судна i с полным оборотом h:

```text
Постоянная часть = сумма A_i * P_i
Коэффициент выбранного рейса = F_i + h_i * (R_i - P_i)
```

MILP минимизирует вторую часть в копейках. Постоянная часть одинакова для всех
планов и прибавляется при независимой оценке стоимости. Она не включается
в ограничения промежуточной цели. При P > R коэффициент рейса может быть
отрицательным: модель может предпочесть больше активности, чтобы уменьшить
дорогое ожидание. Это следствие выбранной схемы, которое надо обсудить с Лизой.

Для оптимизации горизонт должен покрывать готовность **всех допустимых
кандидатов** рейсов. Короткий горизонт отклоняется с минимально необходимым
значением: он не должен незаметно сократить физически допустимую поставку.
Для отдельной оценки готового плана достаточно покрыть его рейсы.
Пропущенные ставки, неоднозначные условия или слишком большие для точного
денежного сравнения коэффициенты отклоняются до вызова решателя.

Результат экономического сравнения включает `planning_strategy`,
`objective_priority`, снимок `cost_terms` и блок `costs` с `baseline`, `planner`,
`equal_volume`, `scenario_difference_rub`, `actual_savings_rub=null`.
Если READY недопустим, его стоимость не считается нулевой — она отсутствует.
При разном объёме разность затрат не выдаётся за экономию одинаковой работы.

## Проверка нового выбора на простом случае

```sh
yana plan examples/economic-choice.json --strategy trips --cost-terms examples/economic-choice.costs.json --time-limit 2 --out outputs/economic-choice/trips
yana plan examples/economic-choice.json --strategy cost --cost-terms examples/economic-choice.costs.json --time-limit 2 --out outputs/economic-choice/cost
```

Это специально сконструированный учебный пример. Доступны два судна: A до 20 т,
B до 10 т. Условные расходы рейса 1000 и 100 руб., часовые ставки явно нулевые
для изоляции влияния рейсового расхода.

| Режим | Принято, т | Рейсы | Стоимость по тестовым ставкам, руб. | Последняя приёмка, ч |
| --- | ---: | ---: | ---: | ---: |
| trips | 20 | 1, судно A | 1000 | 3 |
| cost | 20 | 2, судно B | 200 | 8 |

Меньшие затраты здесь сопровождаются более поздней приёмкой, всё ещё до срока
13 ч. Если рейс A стоит 50 руб., экономическая стратегия выбирает A.
Если сократить срок до 4 ч, дешёвое судно B само не выполнит цель: модель
выбирает полный объём на A. Эти случаи проверяются автоматическими тестами.
Цифры не являются ставками или эффектом реального оператора.

Если задана скорость погрузки, оборот зависит от партии. Экономическая цель
использует длительность конкретного кандидата, а не одну длительность на судно.
См. [погрузку по тоннажу](loading-rate.md).

В CLI новый режим подключён к `plan` и `replan`, включая задержку поступления
и погодный запрет. Веб-форма экономические поля пока не передаёт.
Фиксация начатых рейсов сохраняется в экономическом режиме.
Договор погодного события: [weather-events.md](weather-events.md).

## Смысл расчёта

Для судна i:

```text
C_i = N_i * F_i + H_i * R_i + W_i * P_i
A_i = max(0, T - available_i)
W_i = A_i - H_i
C = сумма C_i
```

- N: число выбранных рейсов.
- F: отдельные расходы рейса, руб./рейс.
- H: полная активность, включая погрузку, движение, приёмку, возврат и подготовку,
  судно-часы. H восстанавливается независимым валидатором по расписанию.
- R: ставка этой активности, руб./судно-час.
- A: оплачиваемая доступность судна до общего горизонта T.
- W: оплачиваемое ожидание, судно-часы.
- P: ставка ожидания, руб./судно-час.

В схеме `all_available_time` оплачивается весь заявленный флот, включая суда
без рейсов. Для них N = H = 0, но W может быть положительным. Судно, доступное
после T, не имеет оплачиваемого времени. Ставки F не должны дублировать расходы,
которые уже включены в R и P.

Горизонт задаётся явно и одинаков для двух планов. Он должен включать полную
готовность после всех рейсов, а не только приёмку или возвращение. Автоматического
расширения горизонта под каждый план нет: оно сделало бы сравнение несопоставимым.
Для будущего интерфейса можно предложить общий горизонт
`return_cutoff_h + max(prep_h)`; в текущем шаге это не автоматический default.

## Входной договор для Лизы и Надежды

Пустой шаблон: `examples/costs.per-vessel.template.json`.

```json
{
  "billing_mode": "all_available_time",
  "currency": "RUB",
  "horizon_h": 492,
  "vessel_rates": {
    "SIM-A": {
      "separate_trip_operations_rub": null,
      "active_vessel_hour_rub": null,
      "waiting_vessel_hour_rub": null,
      "rate_basis": "unspecified",
      "source": null
    }
  }
}
```

Нужна запись для **каждого** судна входного сценария. Ключ — точный ID судна.
Пример выше сокращён до одного судна; для R03 нужны SIM-A и SIM-B.

| Поле | Правило |
| --- | --- |
| `billing_mode` | Только явно выбранная `all_available_time` |
| `currency` | RUB, при отсутствии — RUB |
| `horizon_h` | Конечное неотрицательное число часов, обязательно |
| Три ставки | JSON-числа >= 0, точность до копейки |
| `rate_basis` | `scenario`, `documented` или `unspecified` |
| `source` | Текстовый источник; обязателен для `documented` |

Время и тоннаж транспортной модели остаются целыми. Для совместимости прежний
экономический API допускает дробный оплачиваемый горизонт. Результат компоненты
ожидания округляется до копейки отдельно по каждому судну, половина копейки вверх.
Рейсовые и активные расходы при целых часах и ставках до копейки считаются в целых
копейках. Общий итог складывается из округлённых компонент.

Пропуск ставки или `null` возвращает `status="missing_cost_inputs"`,
`total_rub=null` и точные пути отсутствующих полей. Ноль — допустимая **явно
заданная** ставка. Неизвестные ID, смешение двух форматов, отрицательные ставки,
NaN, бесконечность, строки вместо чисел и ставки точнее копейки отклоняются.
При `documented` приложение сохраняет указанный источник, но не подтверждает его
подлинность и применимость договора автоматически.

Старый формат трёх ставок верхнего уровня сохранён: они одинаково применяются
ко всем судам. Его нельзя смешивать с `vessel_rates`. Старый пустой шаблон
`examples/costs.template.json` продолжает работать.

## Выход для будущего интерфейса

Существующая функция `economics.cost(cfg, plan, deadline, terms)` возвращает:

- `status="scenario_cost"`, `currency`, `billing_mode`, `rates_format`;
- `total_rub`: общий итог;
- `components`: `separate_trip_operations_rub`, `active_time_rub`, `waiting_time_rub`;
- `accepted_t`, `active_vessel_h`, `paid_waiting_h`, `horizon_h`;
- `per_vessel`: записи `vessel_id`, `trip_count`, `available_vessel_h`,
  `active_vessel_h`, `paid_waiting_h`, `rates`, `rate_basis`, `source`,
  `components`, `total_rub`;
- `actual_savings_rub=null` независимо от происхождения введённых ставок.

`rates_format` равен `uniform` или `per_vessel`. JSON-ответ не содержит Decimal.
Денежные значения в JSON — числа рублей до двух знаков после запятой, интерфейс
форматирует их для отображения.

Функция `compare_cost` требует два допустимых плана с одинаковым принятым
объёмом. `scenario_difference_rub = baseline.total_rub - alternative.total_rub`.
Положительное значение означает меньшие сценарные расходы альтернативы.
Отрицательная разность сохраняется: она не превращается в нулевую «экономию».
Каждый допустимый частичный план можно оценить отдельно, но сравнивать разный
объём как экономию одинаковой работы нельзя. На этом шаге нет нового HTTP API:
фронт подключим после интеграции экономической стратегии в ядро и service.

## Воспроизводимая проверка через существующую CLI

Из корня репозитория, в активной виртуальной среде:

```sh
yana cost examples/r03.json demos/static/results.json --deadline 328 --terms examples/costs.per-vessel.demo.json --out outputs/economics-step1.json
```

`costs.per-vessel.demo.json` содержит **вымышленные тарифы для проверки арифметики**.
Для сохранённых планов R03:

| Показатель | READY | MILP |
| --- | ---: | ---: |
| SIM-A: рейсы | 3 | 2 |
| SIM-A: активность, ч | 318 | 212 |
| SIM-A: ожидание до 492 ч | 174 | 280 |
| SIM-A: стоимость при тестовых ставках, руб. | 36540 | 26000 |
| SIM-B: стоимость при тестовых ставках, руб. | 47940 | 47940 |
| Общая сценарная стоимость, руб. | 84480 | 73940 |

Разность 10540 руб. — следствие выбранных тестовых тарифов, а не подтверждённая
экономия перевозчика. Расписания здесь сохранённые: команда `cost` не запускает
решатель и не доказывает, что какой-то план минимален по стоимости.
