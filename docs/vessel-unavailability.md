# A2: адаптация к временной недоступности судна

Реализовано 10 ноября 2026 года по запросу руководительницы, с помощью
ChatGPT/Codex. Запуск и автоматические проверки выполнены ассистентом.
Самостоятельное повторение A2 участницами пока не зафиксировано.

## Условия

Исходный R03: 1650 т, поступления 825 т в час 0 и 825 т в час 120,
два условных судна, одно место погрузки и одно место приёмки. Срок приёмки
328 ч, предел возврата 492 ч. Новое сообщение появляется в час 60:

```json
{
  "type": "vessel_unavailable",
  "announced_at_h": 60,
  "vessel_id": "SIM-A",
  "from_h": 120,
  "to_h": 200
}
```

Все операционные числа сценарные. Интервал не выдаётся за реальную
недоступность какого-либо судна. В этом опыте нет задержки поступления топлива;
он проводится отдельно от A1, а не как одновременное наложение двух изменений.

## Правило и работа программы

Судно содержит необязательное поле `unavailable_intervals`, например
`[[120,200]]`. Границы задаются целыми неотрицательными часами, начало меньше
конца. Отсутствие поля сохраняет прежний сценарный контракт без дополнительных
интервалов. Явный null означает неизвестное значение и требует подтверждения.

Недоступность относится к полному обороту: погрузка, гружёный ход, выгрузка,
возвращение и подготовка к следующему рейсу. Полуоткрытые интервалы позволяют
завершить оборот ровно в 120 ч или начать погрузку ровно в 200 ч.

1. `domain.py` проверяет и нормализует вход, не меняя объект вызывающей стороны.
2. `planning.py` исключает запрещённые варианты ещё до решения MILP. READY
   использует тот же допустимый набор вариантов. Новый предел не сводится
   к переносу `available_h`, который мог бы задним числом запретить старый рейс.
3. `replanning.apply_event` добавляет интервал на копии входа. Начало интервала
   не может предшествовать объявлению; неизвестное судно отклоняется.
4. Первоначальное сравнение получает исходный вход без нового интервала.
   Оба метода узнают сообщение в один момент и сохраняют собственные отправления,
   начатые к этому моменту включительно. Новые отправления — строго позже.
5. Независимый `validation.check_schedule` заново восстанавливает обороты
   и проверяет пересечения, не импортируя генератор вариантов планировщика.
6. При конфликте нового ограничения с уже начатым рейсом возвращается
   `requires_intervention`; тоннаж результата остаётся неизвестным, а не нулевым.

В JSON результата сохранён `initial_input` и контрольная сумма первоначального
входа. Отчёт показывает сообщение понятным текстом над таблицей. Для старых
файлов без исходного входа прежний момент поступления не угадывается.

## Проверенный результат

| Показатель после сообщения | READY | MILP |
|---|---:|---:|
| Принято к сроку, т | 1650 | 1650 |
| Недопоставка, т | 0 | 0 |
| Рейсы | 6 | 5 |
| Последняя приёмка, ч | 280 | 264 |
| Занятые судно-часы | 468 | 404 |
| Средневзвешенная приёмка, ч | 159,758 | 141,091 |

Оба плана прошли независимую проверку; начатые рейсы сохранены, обороты SIM-A
обходят [120,200). Три стадии MILP завершились со статусом optimal: максимум
тоннажа, минимум рейсов и минимум последней приёмки при фиксированных предыдущих
целях. Средняя приёмка и расходы не оптимизируются отдельной целью; у других
равноценных решений они могут отличаться.

В данном опыте MILP делает на один рейс меньше и завершает приёмку на 16 ч
раньше при одинаковом объёме. Рублёвый эффект не установлен. Для экономики
нужно отдельно определить условия оплаты времени недоступности и состав ставок.

Дополнительная проверка с началом недоступности в час 80 при объявлении в 60 ч
конфликтует с уже начатыми оборотами SIM-A. Для обоих методов получен
`requires_intervention`, без выдуманного доставленного тоннажа.

## Как воспроизвести

После установки проекта по README, из папки репозитория:

```sh
python -m yana_planner replan examples/r03.json --event examples/vessel_unavailable.json --deadline 328 --reference examples/r03.reference.json --time-limit 10 --out outputs/vessel_unavailable
python -m yana_planner summarize outputs/vessel_unavailable/results.json --out outputs/vessel_unavailable/summary.json
```

Смотрите `report.html`, `results.json`, `schedule.csv`, `events.csv` и
`summary.json`. Для поиска без известного исходного плана уберите `--reference`.
При ограничении времени результат может отличаться; необходимо смотреть статусы
решателя, допустимость и разрыв, а не только совпадение контрольных чисел.

Добавлено 14 тестов в `test_vessel_events.py`, весь проект — 104 успешных теста.
Проверены полный оборот и границы, работа настоящего решателя без отбрасывания
недопустимого оптимума, отсутствие знания будущего, сохранность истории,
конфликт начатого рейса, неизвестные входы и вывод отчёта. Проверка A1 сохраняется.

Обработка нескольких последовательных сообщений и динамическое изменение
партии A3 остаются отдельными задачами; по реализации A2 они не считаются готовыми.
