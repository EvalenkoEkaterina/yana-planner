# Погодные условия Шапиловой

Первая версия — воспроизводимая проверка расписания на историческом реанализе погоды.
Это не собственная обученная модель, не архив прогноза, доступного диспетчеру в прошлом,
и не подтверждение безопасности судоходства. Общие файлы ядра и интерфейса не изменены.

## Данные и сезон

Источник: [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api),
модель ECMWF ERA5, почасовой ветер на высоте 10 м, м/с, UTC. Реанализ сочетает
наблюдения и модель; значения не являются непосредственными измерениями на судах.
Атрибуция: Open-Meteo и ECMWF ERA5, CC BY 4.0.

Сохранены 9–31 августа 2026 года для двух точек:
Нижнеянск 71.44030, 136.13585 и Усть-Куйга 70.00208, 135.54877.
Координаты и зона Asia/Vladivostok получены через Open-Meteo Geocoding
(названия запросов Nizhneyansk и Ust-Kuyga). Фактические координаты ячеек ERA5
сохранены отдельно в ответах API. Две ячейки не покрывают все локальные условия маршрута.
URL запросов, время получения и контрольная сумма исходного ответа находятся в JSON.

В опыте явно задаётся T0 = 10 августа 2026, 08:00 +10:00. Это привязка учебного R03,
а не дата фактической поставки. Горизонт 492 ч охватывает возвраты и заканчивается в августе.
По [сообщению администрации Ленского бассейна](https://www.albvvp.ru/press-center/news/novosti-organizatsii/itogi-arkticheskoy-navigatsii-2026-goda-zakrytie-sudokhodnoy-obstanovki-na-rekakh-yana-i-indigirka/)
судоходную обстановку Усть-Куйга — Нижнеянск закрыли 30 сентября 2026 года.
Это сезонный контекст, не автоматическое разрешение любого августовского рейса.
Ледообразование, глубины и ограничения осадки эта версия не рассчитывает.
Описанный источником шторм на баре Яны не переносится на весь наш участок.

## Сценарное правило

Максимум ветра в двух ячейках >= порога превращается в закрытие обоих плеч движения
на один час [h,h+1). Смежные часы объединяются. Это условная пространственная и
временная интерпретация данных, а не установленная эксплуатационная зависимость.
Погрузка и выгрузка не закрываются. Стоянка посреди плеча не моделируется.
Сетка 8/10/12 м/с задана для чувствительности, ни одно значение не является нормативом.
Порог требует подтверждения перевозчиком для судна, участка и операции.

На часе 60 условно сообщается о будущих ограничениях. Начальный план получает
только исходный R03. Погодные интервалы начинаются строго после 60 ч.
Данные реанализа будущих часов используются как сценарное сообщение, а не выдаются
за известный заранее прогноз. Поэтому опыт не измеряет качество прогнозирования.
Пропуск значения, ошибочные единицы или неполное покрытие вызывают ошибку.

## Предлагаемый контракт для интеграции

```json
{
  "type": "weather_closure",
  "announced_at_h": 60,
  "closures": [[120, 132]],
  "rule_status": "scenario_assumption",
  "data_kind": "reanalysis",
  "forecast_issued_at": null,
  "t0": "2026-08-09T22:00:00+00:00",
  "horizon_h": 492,
  "threshold_ms": 10,
  "sources": []
}
```

Пример интервала условный. Конструктор заполняет sources реальными запросами.
Время измеряется в целых часах от общего T0; интервалы полуоткрытые.
Это отдельный контракт адаптера; схема общего Scenario не расширяется.
`build_weather_event` строит событие, `apply_weather_event` возвращает копию входа
с существующим полем closures, `assess_weather` проверяет и при необходимости
перестраивает план через существующие ready/optimize.
До объявления новый календарь не раскрывается. Исходные объекты не мутируют.

Результат содержит action:
- no_replan_required: исходный план допустим при новых ограничениях;
- replanned: получен новый план, его выполнение цели проверяется отдельно по shortfall_t;
- requires_intervention: новые условия затрагивают неизменяемые начатые рейсы.

READY и MILP сохраняют собственные исполненные истории. Последовательность событий
пока не поддержана. Экономический режим команды подключается отдельно после согласования API.
Веб-интеграция остаётся Аверкиевой; предлагаемые поля: источник, вид данных, T0,
порог и его статус, момент сообщения, интервалы, action, объём и недопоставка, solver.
Нельзя обозначать все эти случаи общим зелёным статусом «план выполнен».

## Запуск

Из корня репозитория после установки обычных зависимостей:

```sh
source .venv/bin/activate
python scripts/weather_demo.py
python -m unittest discover -s tests -p test_weather.py -v
```

Демо работает без сети. Полный результат: outputs/weather/results.json.
Каждый запуск заново ищет исходный MILP-план с лимитом времени, поэтому его расписание
может различаться; статусы решателя сохраняются.

Обновление снимков требует сети и системного curl, но не новых Python-зависимостей:

```sh
python scripts/fetch_weather.py
```

Скрипт перезаписывает только два именованных погодных снимка. Проверка TLS включена.
Не меняйте даты выборки без согласования T0 и полного покрытия горизонта возвратов.
Следующий этап прогноза — отдельные архивные выпуски с временем инициализации,
доступным горизонтом и датой доступности данных; бесшовный исторический ряд сам по себе
не доказывает, что диспетчер мог знать все значения на часе 60.

## Наглядный отчёт

Демо также создаёт outputs/weather/report.html: график максимума ветра в двух
точках, интервалы с пиковыми значениями и сравнение объёмов.
Сопоставляются три состояния: без погодных ограничений, планирование при
заранее известном сценарном календаре и сообщение на 60-м часу.
В заблаговременном опыте ограничения заданы для часов строго после 0 до
первого запуска планировщика; обязательных рейсов ещё нет. Это опыт с условно
известными будущими условиями, а не воспроизведение оперативного прогноза.
Он не доказывает качество прогноза или экономию. Все пороги сохраняются.
Погодное событие с календарной привязкой отклоняется, если его T0 не совпадает
с T0 перевозки; разные UTC-смещения одного момента допускаются.

## Настройки маршрута

Профиль examples/weather_rules/yana_wind.json содержит версию, идентификатор
маршрута и правила, выбранные точки, показатель и единицы, порог, сетку чувствительности,
область действия и объяснение основания. scripts/weather_demo.py читает этот файл.
Новые зависимости не нужны. event_from_rule проверяет настройки и происхождение
выбранных точек; конфигурация сохраняется в событии. Поле route_id передаётся
в копии входа; общая модель не меняется.

Поддержанный профиль: ветер 10 м, м/с, максимум выбранных точек, сравнение >=,
запрет обоих плеч движения для всего маршрута и всех судов. Для другого маршрута
нужны его точки и обоснованные правила, не переименование данных Яны.
Неизвестные поля отклоняются. Точки не подменяются и не добавляются автоматически.
Иной участок, отдельное судно, погрузка, видимость, изменение длительности и
предел загрузки пока явно отклоняются. Наличие поля в архитектуре не означает
реализацию соответствующего воздействия. Нормативный статус пока не принимается.
Низкоуровневые функции weather.py сохранены для совместимости; новым интеграциям
следует использовать event_from_rule, затем apply_weather_event/assess_weather.

## Собственная обученная модель

Сейчас есть 23 дня (552 часа) в двух точках. Это связанные во времени данные,
а не 1104 независимых погодных ситуаций. Журнала фактических рейсов, причин
задержек и эксплуатационных запретов нет. Модель не обучена.

Реалистичный исследовательский следующий шаг — коррекция внешнего прогноза
ветра с фиксированным упреждением, например 24 часа. Нужны совпадающие по месту
и сроку прогнозы, доступные на момент принятия решения, и независимые наблюдения.
При проверке относительно ERA5 вывод будет о согласовании с реанализом, не
точности относительно измерений. Нельзя брать будущий реанализ как доступный
оперативный признак.

Источники для сбора:
- https://open-meteo.com/en/docs/historical-weather-api — ERA5, длинная история;
- https://open-meteo.com/en/docs/previous-runs-api — прогнозы с упреждением 1–7 дней,
  большинство моделей архивируются с января 2024; наличие нужной переменной,
  места и дат надо проверить фактической выгрузкой.

План проверки: несколько навигационных сезонов; ранние периоды для обучения,
поздний отдельный сезон для теста; промежуток между выборками с учётом горизонта.
Сравнить с исходным внешним прогнозом и простым прогнозом сохранения значения.
Показатели: MAE скорости ветра, ошибки пропуска и ложного срабатывания превышений
сценарного порога. Проверить число независимых эпизодов и перенос на другой
участок. Порог не становится нормативом после обучения.

Модель задержки рейса требует другой целевой переменной: фактической задержки
с её причиной и контекстом (судно, загрузка, участок, операции). Обучение на метках,
порожденных нашим правилом «ветер >= порога», лишь воспроизведёт это правило и
не подтвердит реальную допустимость рейса. Решение о достаточности данных
принимается после аудита покрытия, качества и теста, а не по одному числу строк.

## Погодный раздел сайта

Откройте `/weather` и нажмите «Рассчитать влияние погоды». Расчёт READY/MILP
работает офлайн на включённых снимках ERA5, с общим тайм-аутом приложения.
Каждый результат сохраняется отдельно в SQLite: история находится на погодной
странице. Обновление сохранённого результата не запускает расчёт заново.
Скачать полный результат можно со страницы расчёта.
Порог 8/10/12 м/с остаётся сценарным допущением. Конфликт с начатыми рейсами
отображается как необходимость вмешательства диспетчера.
Если `outputs/weather/results.json` отсутствует в свежем клоне, страница предлагает
выполнить новый расчёт; предварительный запуск демо не требуется.

Исследование коррекции прогнозов описано отдельно в `docs/forecast-model.md`.
Оно не включается в погодный опыт автоматически: рабочая коррекция пока не
прошла отбор, а ERA5 в опыте остаётся историческим реанализом.
