# Прототип речного графа

Реализован первый этап: выбор двух пунктов из небольшой тестовой сети → кратчайший
путь по сумме километров → перенос в существующий расчёт → сохранение пути и сети
в истории и полном отчёте. Поиск пути — Дейкстра, независимый от READY/MILP.

## Как проверить

На главной странице открыть «Выбрать пункты в тестовой речной сети».
А → В: путь А → Б → В, 100 условных км; альтернатива через Г — 130 км.
А → «Тестовый пункт вне сети»: сообщение об отсутствии пути.
Все названия, соединения и расстояния вымышленные, не изображают реальную реку.

Для переноса пути подтвердить использование текущих судов и поставок как учебных.
Тарифы, события и общий календарь запретов движения сбрасываются. Время движения
каждого судна задаётся вручную. При необходимости заново ввести ставки и события.
Остальные параметры транспортной модели, включая календарь грузоподъёмности,
переносятся как учебные и требуют проверки пользователем.

Граф не изменяет математические цели планировщика и не доказывает проходимость.
Промежуточные пункты — прохождение, без приёмки или погрузки. Все суда в первом
прототипе используют один выбранный путь, альтернативные пути не сравниваются MILP.
Кратчайший по километрам путь не обязательно самый быстрый, дешёвый или допустимый.

## Данные от Нади

Файл `src/yana_planner/static/data/river-network.demo.json` — только тестовая сеть.
Ядро `river_graph.validate_network/shortest_path` принимает отдельный словарь сети:

- `network_version`: `yana-river/1`, `id`, `label`.
- `nodes`: список `{id, name}`. В будущем можно добавить координаты.
- `edges`: `{id, from, to, length_km, bidirectional, status, source}`.
- `length_km` — положительное расстояние вдоль водного пути; неизвестное не заменять
  прямой линией или нулём, такой участок пока не включать в поиск.
- `bidirectional` задаётся явно; одинаковая длина не означает одинаковое время туда/обратно.
- `status`: `documented` или `scenario_assumption`.
- `source`: ссылка/документ для подтверждённых данных, описание допущения для тестовых.

Перед публикацией реальной сети нужна проверка географии, расстояний и маркировок
интерфейса: текущая версия намеренно везде названа тестовой. Принадлежность данных
к статусу `documented` сама по себе не является независимой проверкой источника.

## Интерфейс сервера

- GET `/api/river-network`: текущая тестовая сеть.
- POST `/api/river-path`: `{origin_id, destination_id}`; `found` с путём и снимком сети,
  либо `no_path`. Ошибочные пункты/совпадающие пункты: HTTP 400.
- `route.graph_path` в пакете `yana-route/1` хранит ответ поиска. Сервер повторно
  проверяет путь, расстояние и имена относительно вложенного снимка, не текущего файла.
  Это позволяет воспроизвести сохранённые условия после обновления каталога.

## Автоматизация на нескольких реальных участках — следующий этап

Для небольшой подтверждённой сети можно автоматически подбирать данные по маршруту,
не обучая отдельную модель для каждой пары пунктов. Необходимо согласовать:

1. Погода: координаты/участок, время выпуска и период действия, часовой пояс,
   показатель и единицы, источник, прогноз/наблюдение/реанализ, пропуски.
   Нужна проверка покрытия всех участков и доступности информации на момент решения.
2. Экономика: ставки по судну, состав расходов, горизонт и схема оплаты,
   применимость к маршруту/дате. Не считать тарифы прежнего направления автоматически
   подходящими новому. Плата за весь флот считается один раз, не на каждом участке.
3. Движение: профиль судно × направленный участок, длительности/источник,
   допустимость суммирования, отдельные задержки и ограничения.

Сначала подготовить небольшой каталог совместимых профилей с источниками. По выбору
маршрута собирать подходящие данные, а при пробелах показывать «нет данных» и
запрашивать ручной ввод. Это продемонстрирует автоматическую сборку условий;
сценарные погодные значения не выдавать за работающий реальный прогноз.

Сейчас автоматического подбора погоды/тарифов и расчёта времени по расстоянию нет.
Несколько получателей и учёт времени прохождения каждого участка требуют следующего
расширения модели, не входят в первый прототип.

## Проверка

231 Python-тест и 8 JS-тестов прошли. В 7 новых Python-тестах проверены выбор между
путями, обратное/одностороннее движение, отсутствие пути, ошибки сети, неизменность
времён при импорте, сохранение снимка и вывод пути в полном отчёте. В браузере проверены
поиск, отсутствие соединения, перенос в форму, сброс тарифов и расчёт с сохранением.
