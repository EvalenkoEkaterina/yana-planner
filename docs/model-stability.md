# Локальная проверка устойчивости модели

Запуск: `python scripts/check_model_stability.py` из корня с активированной .venv.
Сводка: `output/model-stability/summary.md` и `summary.json`; каждый вход и результат
сохраняется отдельным JSON. Сначала воспроизводится исходный пример consolidation.

14 условий заданы в скрипте до запуска и не фильтруются по исходу. Проверены время
основного поступления, размер первой партии при неизменном суммарном объёме,
доступность SIM-B, срок приёмки, разные вместимости и скорость погрузки.
Погода, путь и тарифы фиксированы. При изменении доступности меняется оплачиваемое
время судна согласно прежней схеме. Скорость погрузки применяется одинаково к обоим
методам и округляется по существующей модели. Выбор плана — объём/рейсы/приёмка;
стоимость оценивается после, не является оптимизируемой целью серии.

Проверочный запуск: 9 вариантов с большим принятым объёмом MILP, 2 совпадения,
3 остановки из-за горизонта оплаты. Для этих трёх нельзя делать вывод о преимуществе
планировщика: расходный расчёт не завершён. Требуемые горизонты: поступление в 18 ч —
124 ч; доступность SIM-B с 48 ч — 121 ч; погрузка 20 т/ч с подготовкой — 126 ч.
Входы автоматически не исправляются: изменения условий оплаты должен выбрать пользователь.

Сообщение экономики теперь содержит минимальный горизонт с подготовкой и введённое
значение вместо общей ошибки. Физические допущения, цели и расписания не изменялись.

Это проверка чувствительности одного учебного механизма, не статистическая оценка
перевозок и не перенос на все реки. Разные объёмы — не одинаковая выполненная работа;
разницу расходов нельзя автоматически назвать экономией. Реальные скорости/ставки
по-прежнему нужны для пилота.
