# Учёт рисков и распределение ответственности

Статус на 13 ноября 2026: отдельные сценарии и проверки уже работают.
Общая сводка устойчивости по набору сценариев и робастная цель MILP ещё
не реализованы. Документ фиксирует договор команды для следующего шага.

## Кто за что отвечает

| Направление | Содержание | Ответственная |
| --- | --- | --- |
| Расчётный учёт рисков | Проверки допустимости, сравнение сценариев, сохранение истории, статусы результата | Еваленко |
| Погодные данные и правило воздействия | Источник, координаты, единицы, время доступности, порог, интервалы | Шапилова |
| Стоимость и бизнес-риски | Ставки, включения, диапазоны чувствительности, бюджет продукта и финансирование | Ушанова |
| Операционные данные и интерфейс | Достоверность входов, применение на участке, отображение допущений и результатов | Аверкиева |

Порог ветра и безопасность реального движения требует подтвердить оператор.
Разработчица не назначает физический порог как установленный факт.

## Где сейчас находятся условия

- `examples/weather-closure.json`: пример события запрета движения, объявление,
  интервалы, тип данных и статус правила. Пример синтетический.
- `examples/arrival_delay.json`: событие задержки поступления.
- `examples/ushanova/vessel_rates.csv`: ставки судов, источник и статус.
- `examples/ushanova/terms.json`: схема оплаты и общий горизонт, а также
  единые параметры отдельного исследования чувствительности.
- `examples/ushanova/terms.per-vessel.json`: собранный из CSV профиль оптимизатора.
- Входной JSON сценария: суда, поступления, вместимости, скорости и длительности.
- `reports/ushanova/`: переоценка сохранённых планов по тарифной сетке и бюджет.
- Выход конкретного нового расчёта: JSON, HTML и CSV в выбранном `outputs/`.

Риски не прячутся в программных константах. Сначала описываются источник,
смысл и сценарные параметры, затем эти параметры передаются действующей модели.

## Что уже проверяем

| Риск | Действующий механизм | Что читать в результате |
| --- | --- | --- |
| Задержка топлива | `arrival_delay`, пересчёт будущего | Принято, недопоставка, сроки, сохранённые рейсы |
| Запрет движения | `weather_closure` на гружёный ход и возврат | Допустимость, новые отправления, вмешательство |
| Новый запрет затронул начатый рейс | Фиксация истории и `requires_intervention` | Неизвестный результат вместо придуманного нуля |
| Изменение тоннажа погрузки | Производительность и точная часовая длительность | Погрузка, оборот, занятость и стоимость |
| Неизвестные или иные тарифы | Пропуски не равны нулю, индивидуальные ставки, сетка чувствительности | Статус стоимости, состав и условная разность |
| Недостаток времени поиска | Бюджет, повторы, отдельные статусы | Допустимость отдельно от доказательства оптимума |
| Слабая переносимость погоды между регионами | Пока методический риск, не готовая метрика | Нужна отдельная проверка на Яне |
| Нет эксплуатационных данных по другому участку | Происхождение входов и сценарные отметки | Нельзя объявлять другую реку проверенным внедрением |

Код не оценивает вероятности происшествий и не подтверждает реальную безопасность.
Денежный оптимизатор минимизирует сценарную стоимость при максимальном принятом
объёме. Он пока не минимизирует ожидаемые потери или худший результат по набору
погодных будущих состояний.

## Следующая расчётная задача Еваленко

Сводка устойчивости одного исходного плана. Для неё надо:

1. Сохранить один конкретный исходный план и его условия. Не запускать новый
   исходный поиск отдельно для каждого опыта и не сравнивать случайно разные планы.
2. Согласовать с командой набор отдельных событий: задержка или запрет движения.
   Параметры из источника либо явно сценарные. Совместный пакет нескольких событий
   требует отдельной реализации — текущая функция обрабатывает одно событие.
3. Для каждого события проверить исходный план без изменений, затем отдельно
   попробовать перепланирование с тем же начатым префиксом.
4. Выдать строку на опыт: допустимость, принято/недопоставка, последняя приёмка,
   необходимость вмешательства, стоимость при допустимом плане, статус оптимума.
5. Общую стоимость сравнивать как экономию только при одинаковом принятом объёме
   и одной схеме/горизонте оплаты. Неподтверждённые результаты оставлять null.

Число успешных условных сценариев можно назвать покрытием проверенного набора,
но нельзя выдавать за вероятность успешной доставки. Частота реальных событий,
распределения и ошибки прогноза должны быть оценены отдельно.

Если позже выберем один план, устойчивый ко всем сценариям, потребуется новая
математическая постановка. Это отличается от текущего пересчёта после события.

## Перенос погодной модели и более широкая география

Сейчас по другим регионам у команды есть погода, а не полный набор транспортных
данных. Погодный модуль можно расширять на новые координаты. Перенос прогноза
с другого региона проверяется на отдельном временном отрезке Яны и сравнивается
с простой базой. Прогноз ветра не равен прогнозу задержки судна.

Реанализ используется для исторических сценариев, а не как прогноз, известный
диспетчеру заранее. Для настоящего прогноза сохраняются дата выпуска и
фактическая доступность информации. Время инициализации модели не обязательно
совпадает с доступностью её результатов. Нельзя обучаться на будущих данных.

Расширение всей логистики на другой участок требует флота, длительностей,
причалов, поступлений, ёмкостей, потребления и стоимости. Одна карта погоды
не доказывает проверенность расписания на другом маршруте.
