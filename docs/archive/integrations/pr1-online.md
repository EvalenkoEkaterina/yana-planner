## Разрешение конфликтов

В domain.py, planning.py и validation.py сохранена проверенная версия команды:
она уже поддерживает те же полные обороты и сохраняет старые контрольные суммы
входов без необязательного поля. Исходная версия PR и тесты доступны в истории.

Публичные имена функций участницы сохранены в online.py. Вместо второго
планировщика они используют общие apply_vessel_unavailable, replan и run_replanning.
Её восемь тестов включены в общий набор. Исправлен только неточный комментарий
о длительности оборота: 64 ч вместо 56 ч, без изменения поведения теста.

## Два входных формата

| Источник | Тип | Границы |
|---|---|---|
| Общий формат | vessel_unavailable | from_h=120, to_h=200 |
| Формат PR №1 | vessel_unavailability | interval=[120,200] |

compat.normalize_event возвращает копию общего формата. Исходное сообщение
в полной цепочке сохраняется как source_event. Если представлены обе формы
границ и они противоречат друг другу, расчёт отклоняется. Неполные и неизвестные
значения не заменяются нулями. По общему контракту начало нового ограничения
не может предшествовать объявлению; ретроспективные сообщения отдельно не поддержаны.

## Формат результата

Старые revised_ready / revised_milp принимаются как revised_baseline /
revised_planner. Функция run_unavailability_experiment сохраняет оба набора
имён для существующих вызывающих программ. Алиасы создаются как отдельные
копии; если они впоследствии расходятся, чтение отчёта отклоняется, а не
молча выбирает один вариант.

В старом сохранённом результате scenario_id берётся из существующего initial.
Отсутствующий initial_input не восстанавливается по догадке. Статусы, тоннаж,
начатые рейсы и неизвестные величины не меняются адаптером. Сам адаптер не
подтверждает допустимость рейса: она остаётся задачей validation.check_schedule.

Команда report требует отдельную выходную папку и отказывается писать поверх
папки исходного файла.

Исходные outputs_online/unavailability_experiment.json и comparison.csv не
перезаписывались. Отчёт REPORT.md дополнен текущим статусом и ссылкой на PR.
Различие средней приёмки между равноценными по трём целям планами допустимо.

## Проверенные цепочки

1. Старый Python API участницы → общая модель → экспорт → общая сводка.
2. CLI replan с её исходным JSON события → отчёт → CLI summarize.
3. Её ранее сохранённый JSON → CLI report → полноценные строки «до/после».
4. Серия сроков с её форматом события → аудит истории и входа → сводка.
5. Ошибочный/противоречивый вход → явная ошибка; прежний успешный summary
   не остаётся текущим результатом после неудачного report.

```sh
python -m yana_planner replan examples/r03.json --event examples/vessel_unavailability.json --deadline 328 --reference examples/r03.reference.json --time-limit 5 --out outputs/pr1_live
python -m yana_planner summarize outputs/pr1_live/results.json --out outputs/pr1_live/summary.json
python -m yana_planner report outputs_online/unavailability_experiment.json --out outputs/pr1_saved
```

В R03 после недоступности [120,200) оба метода принимают 1650 т. READY:
6 рейсов, последняя приёмка 280 ч; MILP: 5 рейсов, последняя приёмка 264 ч.
Общая сводка корректно показывает разницу 1 рейс и 16 ч при одинаковом объёме.
Входы сценарные, реальная экономия не устанавливается.

Весь набор - 134 успешных теста: 112 прежних, 8 из PR и 14 новых проверок
совместимости. Дополнительно цепочки повторены на полном R03 и исходном
сохранённом файле PR; проверки и интеграцию выполнил ассистент по запросу
руководительницы. Изменения из архива H этим этапом не исправляются и не включаются.
