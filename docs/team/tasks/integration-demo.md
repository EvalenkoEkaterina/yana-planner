# INT-01. Единый запуск и понятный отчёт

**Ответственная:** Еваленко Екатерина. **Роль:** инженер по интеграции и проверке качества.

**Статус:** задание на следующий этап, ещё не реализовано. **Оценка:** 4-6 часов при готовом окружении; время на изменения ядра сюда не входит.

## Что нужно получить

Сделать один воспроизводимый запуск, который выполняет согласованные опыты, собирает результаты в одну таблицу и открывает путь к каждому подробному отчёту. Другой участник должен повторить его без ручного переноса цифр.

Это твоя инженерная часть: связать готовые модули, проверить результаты и сделать демонстрацию понятной. Переписывать оптимизатор для этой задачи не требуется.

## На что уже можно опираться

- `planning.compare` строит исходное сравнение.
- `replanning.run_replanning` выполняет один шаг обновления.
- `experiments.summarize_experiment` извлекает проверенные показатели.
- `io.export_result` сохраняет отдельный отчёт и таблицы.
- CLI уже умеет `plan`, `replan`, `summarize`, `report`.

Перед интеграцией посмотреть сигнатуры функций в текущей версии. Не создавать вторую реализацию проверки или формул сводки.

## Шаг 1. Зафиксировать набор опытов

Подготовить `examples/demo_suite.json`. Это новый файл задания; сейчас в репозитории его нет.

| Запуск | Вход | Событие | Срок |
|---|---|---|---|
| Контроль | `examples/r03.json` | Нет | 328 ч |
| A1 | Тот же R03 | `examples/arrival_delay.json` | 328 ч |
| A2 | Тот же R03 | `examples/vessel_unavailable.json` | 328 ч |
| A3 | Тот же R03 | `examples/payload_restriction.json` | 328 ч |
| Конфликт A3 | Тот же R03 | `examples/payload_restriction_conflict.json` | 328 ч |

Это пять независимых запусков. Условия A1/A2/A3 не складываются друг с другом. Для каждого до старта задать идентификатор, вход, событие или `null`, срок, лимит на ступень и путь к необязательному `reference`.

Файлы в манифесте разрешать относительно корня репозитория. Режим с `reference` явно обозначить; запуск без него считать отдельным режимом, не скрытым повтором до получения красивых чисел.

## Шаг 2. Собрать запуск

Создать `scripts/run_demo.py`. Предлагаемый интерфейс после реализации:

```sh
python scripts/run_demo.py --suite examples/demo_suite.json --out outputs/team_demo
```

Программа должна:

1. Прочитать и проверить весь манифест до начала расчётов: обязательные поля, существование входов, уникальные идентификаторы и безопасные каталоги результатов.
2. Запустить готовый расчёт для каждого опыта и сохранить его в отдельную папку.
3. Для команд CLI использовать текущий Python через `sys.executable -m yana_planner`; если выбраны вызовы функций, использовать установленный пакет. Не зависеть от локального пути чужого окружения.
4. Получить сводку через существующий `summarize_experiment`. У обновлений сохранить обе фазы: `before` и `after`.
5. Записать `protocol.json`: версию Git и признак локальных изменений, версии Python/зависимостей, входы и SHA-256, параметры поиска, выбранный режим кандидата. В результаты каждого опыта сохранить статусы решателя.
6. Сохранить понятный статус каждого запуска. Ожидаемый конфликт не выдавать за техническую поломку или нулевой тоннаж; неожиданные ошибки не скрывать.

Не перезаписывать существующий комплект молча. Выбрать отказ при непустом выходном каталоге либо явный режим перезаписи с удалением устаревших результатов только внутри выбранного каталога.

## Шаг 3. Сделать общий результат

В `outputs/team_demo/` получить:

```text
protocol.json      Версия, входы, параметры и хеши
summary.json       Сводка для дальнейшей обработки
summary.csv        Общая таблица
index.html         Краткая таблица и ссылки на отчёты
control/           Исходное сравнение
a1/                Задержка топлива
a2/                Недоступность судна
a3/                Ограничение партии
conflict/          Диагностика начатого рейса
```

Для общей таблицы достаточно идентификатора, фазы, срока, статусов, принятых тонн, недопоставки, числа рейсов, последней и средней приёмки, занятости и признака компромисса. Разницы брать из готовой сводки. Человекочитаемые подписи и единицы добавить в HTML.

При разных объёмах не объявлять сокращение рейсов или времени улучшением одинаковой поставки. Неизвестные значения оставить `null`, в HTML показать «нет подтверждённого значения». Фактическую экономию не заполнять. Условную экономику подключать отдельно, только с явными ставками и схемой оплаты.

## Шаг 4. Проверить неприятные случаи

Добавить содержательные проверки обвязки, например в `tests/test_demo.py`:

- Неизвестное событие или отсутствующий файл: понятная ошибка до начала серии.
- Два одинаковых идентификатора: результаты не перезаписываются.
- Разный тоннаж: сводка не рисует фиктивную экономию рейсов.
- `requires_intervention`: конфликт виден, подтверждённые тонны не появляются.
- Непустая выходная папка: старый успешный отчёт не маскирует новый неудачный запуск.

Для тестов обвязки использовать небольшие данные или подмену запуска. Полную серию решателя прогнать отдельно один раз, не повторять её в каждом тесте.

## Когда задача готова

- Все пять запусков сохраняют собственный результат, включая ожидаемый конфликт.
- Таблица получена из JSON, цифры не внесены вручную.
- Планы с допустимым результатом прошли независимую проверку; остальные статусы видны отдельно.
- Другой участник повторил запуск по инструкции и открыл все ссылки из `index.html`.
- Тесты и стиль кода проходят; в Pull Request есть команда запуска и короткий вывод.

Сравнивать с контрольными числами можно, но не требовать совпадения времени при недоказанной оптимальности. Лимит времени и найденный кандидат влияют на результат.

## Что объяснить на защите

«Я отвечаю за воспроизводимость общего эксперимента: согласованные входы, запуск модулей, проверку статусов и итоговый отчёт. Мы отдельно показываем выполнение поставки, компромиссы и ситуации, в которых требуется решение диспетчера».

Нужно самостоятельно уметь объяснить: что изменилось в каждом опыте, какие решения уже нельзя менять, почему допустимый план может не выполнить весь объём и почему меньше рейсов не всегда означает меньшие расходы.
