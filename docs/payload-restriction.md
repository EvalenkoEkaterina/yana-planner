# Перепланирование после временного ограничения партии

11 ноября 2026. Доработка A3 поверх проверенной интеграции экономики.

## Что изменилось

Добавлено событие `payload_restriction`. Изначально READY и MILP получают
только исходный сценарий. В момент сообщения оба узнают временное ограничение,
сохраняют начатые погрузки с их судами, временем и тоннажем, затем пересчитывают
будущие рейсы. Новые старты допускаются строго после часа сообщения.

```json
{
  "type": "payload_restriction",
  "announced_at_h": 60,
  "from_h": 120,
  "to_h": 168,
  "capacity_t": 200
}
```

Все часы и тонны целые. Начало ограничения не может предшествовать сообщению;
интервал имеет положительную длительность и понимается как [from_h,to_h).
Неизвестные величины требуют подтверждения, отрицательные и некорректные
входы отклоняются. Схема сценария 1.0 сохранена: новое событие не меняет
формат уже существующих входов и результатов A1/A2.

## Правило календаря

Внутри нового интервала действует минимум исходного предела и нового
ограничения. Существующие изменения внутри интервала сохраняются, если они
строже. После окончания временного ограничения возвращается исходный предел,
действующий именно на эту дату; это не обязательно 400 т или предел до начала
события. Исходные объекты не изменяются.

Предел проверяется на всём гружёном ходе. Изменение, начавшееся ровно после
окончания гружёного хода, не затрагивает этот рейс. Нулевой предел запрещает
гружёный проход в интервале, но сам по себе не закрывает порожний возврат и
терминальные операции. Для полного закрытия движения есть `closures`.

Ограничение задаётся готовым сообщением. Прогноз погоды, зависимость уровня
воды от глубины и перевод осадки в тоннаж не реализованы.

## Начатый рейс и вмешательство

Если обновлённый календарь делает начатый рейс недопустимым, срабатывает уже
существующая независимая проверка фиксированной истории. Автоматическое
продолжение возвращает `requires_intervention`; итоговые тонны и недопоставка
остаются `null`. Сохраняются событие, обновлённые входы, снимок состояния и
начатые рейсы. В результате добавлено диагностическое поле `conflicts`:
судно, начало погрузки, фактическая партия, допустимый предел и интервалы
пересечения. HTML показывает эти сведения таблицей.

Диагностика использует даты, восстановленные независимым проверяющим модулем,
и не заменяет проверку допустимости. Новый тоннаж не выдаётся за подтверждённый
по диагностическим полям. Функции экономики отклоняют конфликтный результат.

В примере `payload_restriction_conflict.json` в час 60 сообщают о пределе
200 т на [70,100). SIM-B уже грузилось в час 48, несёт 400 т и движется с
грузом в [56,80). Конфликтный участок - [70,80). Оба метода сохраняют рейс,
указывают 400/200 т и требуют решения диспетчера. Программа не моделирует
самостоятельно промежуточную разгрузку или ожидание внутри плеча.

## Полученные результаты

Протокол: R03, 1650 т, объявление в час 60, временный предел 200 т на
[120,168), прежняя сетка сроков 164/246/328/410 ч. На каждой ступени решателя
лимит 3 с. Сохранены все точки. Ранее найденный исходный R03-план используется
как перепроверяемый кандидат; первоначальный план не знает будущего события.
Каждый метод сохраняет свою фактически начатую историю. Это сравнение
политик планирования, а не продолжений с принудительно общей историей.

| Срок, ч | Принято READY/MILP после события, т | Рейсы | Последняя приёмка, ч |
|---|---|---|---|
| 164 | 825 / 1000 | 3 / 3 | 152 / 160 |
| 246 | 1425 / 1650 | 5 / 5 | 224 / 232 |
| 328 | 1650 / 1650 | 6 / 5 | 276 / 232 |
| 410 | 1650 / 1650 | 6 / 5 | 276 / 286 |

При 164 и 246 ч разные объёмы: разность окончания не называется ускорением
одинаковой доставки. При 328 ч полный объём у обоих, MILP экономит один рейс
и заканчивает на 44 ч раньше. По сравнению с исходным сценарием без нового
ограничения окончание MILP ухудшилось с 224 до 232 ч. Доработка обеспечивает
учёт изменившихся условий, а не гарантирует улучшение при ужесточении условий.

При 410 ч найденный MILP-план имеет меньше рейсов, но заканчивает на 10 ч
позже READY; оптимальность третьей цели не доказана. Первые две цели доказаны
во всех четырёх точках. Повышать качество этой точки повторным подбором
лимита для презентации не стали; ограничение поиска сохранено в оценке.

Старые планы заново проверены по новым условиям. При 246, 328 и 410 ч оба
первоначальных плана недопустимы без пересчёта. При 164 ч исходный READY-план
сохранил допустимость, MILP-план стал недопустим. Их ошибочный тоннаж не
используется как результат доставки после события.

## Экономическая оценка

Только для равных принятых объёмов. Иллюстративные ставки: 25000 руб./рейс,
1000 руб./активный судно-час, 500 руб./судно-час межрейсовой паузы.

При сроке 328 ч: активная занятость READY/MILP 510/404 судно-ч,
межрейсовые паузы 8/62 ч, расходы 664000/560000 руб., разница 104000 руб.
До нового ограничения у исходного MILP-плана паузы составляли 30 ч и расходы
544000 руб. Повторно использовать эти числа после A3 нельзя.

При 410 ч разница условных расходов 77000 руб., при этом MILP заканчивает
позже. Нельзя объявлять этот план лучшим по всем показателям. Другие схемы
оплаты могут изменить вывод. Ставки сценарные; фактическая экономия неизвестна.

## Проверка

170 тестов: 148 прежних и 22 новых. Проверены: календарь и его восстановление,
сочетание ограничений, нулевой предел, границы гружёного хода, отсутствие
преждевременного знания, сохранение истории, начатая погрузка, конфликтный
выход, отчёт и CLI, повторная проверка экономики по обновлённым входам.
Пройдены Ruff check и format --check. Численные данные относятся к сохранённым
прогонам; ограниченный по времени повтор может дать другой допустимый план.

```sh
python -m unittest discover -s tests -v
ruff check src tests
ruff format --check src tests
yana replan examples/r03.json --event examples/payload_restriction.json --deadline 328 --reference examples/r03.reference.json --out outputs/payload_update
yana summarize outputs/payload_update/results.json --out outputs/payload_update/summary.json
yana replan examples/r03.json --event examples/payload_restriction_conflict.json --deadline 328 --reference examples/r03.reference.json --out outputs/payload_conflict
```

Последняя команда ожидаемо возвращает код 2, а отчёт содержит конфликт.
Для экономики по-прежнему требуются выбранные ставки и схема оплаты.

## Риски и следующие шаги

| Ограничение | Что это означает | Следующая работа |
|---|---|---|
| Одно сообщение за запуск CLI | Нет автоматической последовательности обновлений | Очередь событий, порядок по времени, история каждого пересчёта |
| Только временное ужесточение с заданным концом | Нет отдельной операции отмены или досрочного ослабления ранее введённого ограничения | Идентификаторы и версии ограничений, сообщения об отмене/продлении |
| Готовый общий предел участка | Нет расчёта из погоды, осадки и конкретного судна | Проверяемый источник ограничений и грузовые характеристики |
| Конфликт с начатым рейсом | Система предупреждает, но не выбирает физический способ разрешения | Согласованные действия диспетчера и отдельная модель этих операций |
| Постоянные времена операций | Маленькая партия имеет прежние длительности | Проверить зависимость погрузки/выгрузки от тоннажа |
| Часовая сетка и лимит поиска | Не все решения и не каждая третья цель доказаны | Тест масштаба, обоснованный лимит и сохранённые допустимые кандидаты |
| Сценарные расходы и операционные входы | Расчётная полезность не равна доказанному эффекту предприятия | Проверка на подтверждённых данных и сопоставимом рабочем плане |
