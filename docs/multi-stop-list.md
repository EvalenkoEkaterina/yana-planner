# Список получателей: контракт для интеграции

Реализовано обобщение в `yana_planner.multi_stop.plan_multi_stop`:
одно судно, один рейс и 1–8 получателей в заданном порядке. `plan_two_stop`
остаётся совместимым входом для прежних примеров с двумя получателями.
Web/API, флаги capabilities и фронт не изменены.

## Вход

Пример: `examples/multi_stop/four-recipients.json`. Поля исходного двухполучательного
контракта сохраняются: SIM_ONLY, явные допущения, источник, поступления, горизонт,
одно судно. `stops` — список из 1–8 уникальных получателей; у каждого:

- id — идентификатор, отличный от отправителя;
- required_t — обязательная положительная партия;
- deadline_h — срок завершения выгрузки;
- unload_h — фиксированная длительность выгрузки;
- windows — непустой список [from_h,to_h), целые часы в горизонте.

`vessel.travel_h` — список длительностей: источник → первый, первый → второй и т.д.
Число записей точно равно числу получателей. `return_h` задаёт отдельную полную
длительность возврата от последнего получателя к источнику без промежуточных операций.
`movement_closures` содержит leg1…legN и return; каждый список задаётся явно.

Старые leg1_h/leg2_h принимаются только для двух получателей. Противоречивые
одновременные travel_h и leg1_h/leg2_h отклоняются. Времена не определяются из
расстояний или погодных координат. Все партии грузятся в источнике за один раз.

## Выбор порядка важности

Необязательное поле верхнего уровня `receipt_priority` — список ID всех выбранных
получателей ровно по одному разу. Порядок списка определяет последовательность
минимизации времени завершения их приёмки. Например:

```json
"receipt_priority": ["ust-kuyga", "kazachye", "batagay", "saydy-verkhoyansky"]
```

`stops` по-прежнему определяет порядок посещения. Если receipt_priority отсутствует,
сохранено прежнее поведение: сначала последний получатель, затем остальные по пути.
Неверные ID, повторы, пропуски и строки вместо списка отклоняются. Никакие
обязательные объёмы, окна или сроки не становятся необязательными.

## Цели и результат

Обязательные объёмы и сроки всех получателей — жёсткие ограничения. Цели
оптимизируются последовательно в receipt_priority с фиксацией доказанных значений,
затем минимизируется готовность после возврата. При недоказанном этапе дальнейшая
иерархия не решается: возвращается найденный проверенный план с неполной доказанностью.

`objective_stop_id` — первый в порядке важности. `primary_receipt_proven` — доказан
оптимум первичной цели, `lexicographic_optimal` — доказаны все этапы. В receipt_optima
по каждому ID и рангу дано optimal_given_higher_priorities: это условная оптимальность
после фиксации более важных целей. Не путать её с безусловным минимумом этой поставки.
`visit_order` и `receipt_priority` возвращаются отдельно.

Для совместимости earliest_last_proven и earliest_second_proven (два получателя)
подтверждают безусловный оптимум последней приёмки только если она выбрана первой
целью. При других приоритетах они false, даже если числа случайно совпали с прежними.
`goal_met` — найдена полная допустимая поставка всем. При невыполнимости plan=null;
окончание времени поиска не выдаётся за доказательство невыполнимости.

`plan.deliveries` содержит по всем получателям stop_id, accepted_t, receipt_h,
cargo_after_t; `plan.starts` — load_start_h, depart1_h/unload1_start_h…departN_h/
unloadN_start_h, depart_return_h. Проверяющий независимо реконструирует движение,
остатки, окна, запреты каждого плеча и возврата, сроки и готовность.

## Демонстрация

`python scripts/check_multi_stop_list.py` → `output/multi-stop-list/report.md` и
result.json. Предлагаемая последовательность Нижнеянск → Казачье → Усть-Куйга →
Сайды → Батагай дана только как полностью учебная перевозка. Новые расстояния и
места выгрузки не подтверждены, времена и партии вымышленные. Проверенный граф
реальных расстояний автоматически новыми рёбрами не расширяется.

В примере загружается 600 т; выгрузки 150/200/100/150 т, приёмки в часы
37/59/81/101, остатки 450/250/150/0 т. Пример не доказывает реальную выполнимость
или экономию. Погода и экономика к этому модулю не подключены.

Проверки: 1, 2, 4 и 8 получателей, нехватка ресурсов, невыполнимый промежуточный
срок, запрет третьего плеча и его влияние на последующие пункты, подменённое
расписание, неполные списки плеч/запретов. Лимит времени пока на этап (по умолчанию
2 с); число этапов N+1. Веб-интеграция должна сохранить отдельный процесс и общий
wall-clock тайм-аут, а также отображать неподтверждённую оптимальность.

## Ограничение содержательного эффекта приоритетов

`python scripts/check_receipt_priorities.py` сравнивает три порядка на одинаковых
входах и сохраняет сводку в `output/receipt-priorities/report.md` и JSON каждого опыта.
Времена совпали. Для фиксированного пути, одного судна, фиксированных партий и
свободного ожидания раннее выполнение предшествующей операции не ухудшает
возможность выполнить следующую раньше. Поэтому приоритетный переключатель здесь
не доказывает операционного выигрыша и не обязан менять расписание.

Для реального конфликта целей потребуется отдельное расширение: распределение
ограниченного ресурса между заказами, общий флот, выбор порядка заходов и т.п.
Такие возможности не добавлены автоматически вместе с receipt_priority.
