# Подключение нового фронта к расчётному ядру

Готово в ветке feature/evalenko-optimizer. Интерфейс Аверкиевой v2 подключён
через адаптер пакета: [статус интеграции](averkieva-server-integration.md).
Старый маршрут POST / продолжает работать. Новый POST /api/plan принимает
полный JSON условий без привязки к R03. Погодный преобразователь команды
должен передать подготовленное событие; API не скачивает погоду.

## Быстрая проверка

Из корня репозитория, после установки зависимостей:

```sh
source .venv/bin/activate
python -m flask --app yana_planner.web:create_app run --port 5001
```

В другом терминале из того же каталога:

```sh
curl --fail-with-body http://127.0.0.1:5001/api/plan \
  -H 'Content-Type: application/json' \
  --data-binary @examples/api/cost-plan.request.json
```

Погодное событие вместе с экономической целью:

```sh
curl --fail-with-body http://127.0.0.1:5001/api/plan \
  -H 'Content-Type: application/json' \
  --data-binary @examples/api/weather-cost.request.json
```

Оба примера полностью синтетические и предназначены для проверки интеграции.
В первом примере при полном объёме 20 т экономический выбор допускает два
дешёвых рейса вместо одного дорогого. Это проверка цели, не реальная экономия.

## Вход

| Поле | Назначение |
| --- | --- |
| scenario | Полный объект существующего формата условий; mode=SIM_ONLY и явные допущения обязательны |
| deadline_h | Положительный целый срок приёмки, не позднее возврата |
| strategy | trips (по умолчанию) или cost |
| cost_terms | Схема оплаты, горизонт, индивидуальные или общие ставки; обязательно для cost |
| event | Необязательное одно событие arrival_delay или weather_closure |
| search_seconds | Строка auto (по умолчанию) либо число 2, 10 или 30; лимит одного этапа |

Приоритет trips: максимальный принятый объём → минимальное число рейсов →
ранняя последняя приёмка. Приоритет cost: максимальный объём → минимальная
сценарная стоимость → ранняя последняя приёмка. READY остаётся одной и той же
базой для сравнения. Пересчёт события использует тот же выбранный приоритет.

Допускается до 6 судов, до 100 записей в каждом календаре. Сроки приёмки
и возврата ограничены MAX_DEADLINE_H (по умолчанию 492 ч). Размер всего
запроса — до 1 МиБ. Это ограничения веб-обработчика, не утверждение о
максимальном масштабе задачи CLI. Настройку масштаба согласовать отдельно.

API не дополняет отсутствующие эксплуатационные параметры учебными числами.
Частичный исследовательский реестр реальных перевозок не является scenario.
Время поступлений, доступности и движения нужно заполнить и обосновать.
cost_terms не создаётся из цены закупки за тонну автоматически.

Для weather_closure действуют docs/weather-events.md: интервалы [a,b),
время объявления, источник данных, сценарный статус правила, временная
проверка прогноза. Погодный запрет не изменяет задним числом начатые рейсы.
Конфликт с уже начатым движением означает необходимость вмешательства.

## Ответ

HTTP 201 означает: вычисление завершено, отчёт сохранён. Это **не** означает
полную поставку или доказанную оптимальность. JSON содержит:

- id — номер сохранённого расчёта;
- inputs — полный снимок условий, события, стратегии, тарифов и настроек;
- result — результаты ядра, проверки, solver, comparisons и report_html;
- links.page — существующая страница расчёта;
- links.report — самостоятельный HTML-отчёт;
- links.json — сохранённый снимок для скачивания.

Ссылки относительные: добавить origin текущего сайта. Их открытие не запускает
поиск повторно. В SQL сохраняется снимок входов и выходов с версией кода.

Без события читать result.baseline и result.planner. С событием — result.initial,
result.revised_baseline.result и result.revised_planner.result.
Удобное общее представление для фронта: result.comparisons.

Перед выводом объёма проверить status=valid_simulation. Затем accepted_t,
shortfall_t и выполнение цели; отдельно — solver и подтверждение оптимума.
Для события проверить status и intervention, не превращать null в ноль.
Денежную разницу как сопоставимый эффект показывать только при одинаковом
принятом объёме и общей схеме оплаты. actual_savings_rub остаётся null.

## Ошибки и ожидание

- 400 / invalid_input: показать error, оставить введённые данные;
- 408 / calculation_timeout: общий бюджет исчерпан, result=null;
- 413 / request_too_large: запрос больше 1 МиБ;
- 500 / server_error: расчёт или сохранение не завершены.

Общий бюджет CALCULATION_TIMEOUT_S по умолчанию 30 с включает подготовку,
исходный расчёт и пересчёт. Он отличается от search_seconds одного этапа.
Вычисление выполняется отдельным процессом; при общем тайм-ауте процесс
останавливается, незавершённый результат в историю не записывается.
408 не является доказательством отсутствия допустимого плана.

## Передача участницам

Надежде: форма v2 уже подключена через POST / с route_package_json и общий
расчётный адаптер; поддержаны ожидание, ошибки и восстановление. Для другого
клиента остаётся POST /api/plan с контрактом выше. Источники пакета сохраняются
при использовании формы; произвольные поля не добавлять в контракт /api/plan.

Шапиловой: передавать event по согласованному контракту; forecast_issued_at
не подменять временем инициализации погодной модели. Конвертер weather.py
в этой ветке по-прежнему не появился, автоматического получения погоды нет.

Лизе: передавать cost_terms с теми же ID судов и согласованным горизонтом;
неизвестные ставки не равны нулю. Сценарный статус ставок сохраняется.

Еваленко: расчётный путь и сохранение интегрированы. Анализ набора рисков
пока запускается отдельной CLI-командой (docs/risk-contract.md), не этим API.
Дизайн формы, погодный конвертер, подтверждённые эксплуатационные входы
и реальная финансовая валидация остаются отдельными задачами команды.
