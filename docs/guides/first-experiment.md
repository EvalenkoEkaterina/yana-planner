## Что сделано

Добавлен `src/yana_planner/experiments.py`, функция `summarize_experiment(result)`
и команда `yana summarize`. Они используют JSON существующих `plan`/`replan`.
Сам оптимизатор и параметры R03 не изменены. Новые события недоступности судна
и ограничения партии на этом шаге не реализованы.

Сводка показывает статусы, тонны, недопоставку, выполнение задания, рейсы,
последнюю и средневзвешенную приёмку, занятость флота, сравнимость объёмов
и компромисс показателей. Реальная экономия остаётся неизвестной.

## Как повторить

В папке репозитория, после установки по README и активации своего окружения:

```sh
python -m yana_planner plan examples/r03.json --deadline 328 --reference examples/r03.reference.json --time-limit 10 --out outputs/my_static
python -m yana_planner replan examples/r03.json --event examples/arrival_delay.json --deadline 328 --reference examples/r03.reference.json --time-limit 10 --out outputs/my_replanning
python -m yana_planner summarize outputs/my_static/results.json --out outputs/my_static/summary.json
python -m yana_planner summarize outputs/my_replanning/results.json --out outputs/my_replanning/summary.json
```

`--reference` передаёт ранее найденный план, который программа заново проверяет.
Он не содержит знания о будущей задержке. После сообщения в 60 ч обновляются
только будущие решения; собственные начатые рейсы каждого метода сохраняются.
При лимите времени возможен другой допустимый результат: смотреть журнал
решателя и не объявлять неполный поиск доказательством оптимальности.

## Контрольные показатели

| Показатель | Исходный READY | Исходный MILP | После задержки READY | После задержки MILP |
|---|---:|---:|---:|---:|
| Принято к сроку, т | 1650 | 1650 | 1650 | 1650 |
| Недопоставка, т | 0 | 0 | 0 | 0 |
| Рейсы | 6 | 5 | 6 | 5 |
| Последняя приёмка, ч | 276 | 224 | 284 | 272 |
| Занятые судно-часы | 510 | 404 | 510 | 404 |

В исходном контрольном плане средневзвешенная приёмка составляет 136,697 ч
для READY и 146,424 ч для MILP. Последняя партия приходит раньше на 52 ч,
но средняя тонна - позже на 9,727 ч. Поэтому `tradeoff=true`.
Время средней приёмки у равноценных по целям MILP-решений может различаться:
оно не является отдельной целью текущего оптимизатора.

Положительное `delta_t` означает больше тонн у MILP. Положительное `*_saved`
означает меньше рейсов/занятости или более раннюю приёмку у MILP. Эти разницы
ресурсов появляются только при равных известных объёмах двух допустимых планов.

Если один план недопустим, диагностические числа из него не становятся
подтверждёнными показателями. Если объёмы различаются, нельзя объявлять более
дешёвой перевозку только потому, что она перевезла меньше. Если не хватает
метрик, отсутствие выявленного компромисса не означает доказанное отсутствие
компромисса: сводка возвращает `null`.

## Один понятный контроль баланса

На 60-м часу у каждого метода в источнике 25 т, на судах 800 т, принято 0 т:

`25 + 800 + 0 = 825 т поступившего топлива`.

У READY на этот момент дополнительно зарезервировано 400 т приёмной ёмкости.
Резерв - это место для части груза, уже учтённого в пути. Его нельзя ещё раз
прибавлять к материальному балансу. Резерв меняет свободную ёмкость, а не
создаёт дополнительное топливо.

## Что сделать самой и записать как собственный вклад

1. Повторить команды в своём окружении и сохранить полученные файлы.
2. Найти в отчёте начало сообщения о задержке, исходные и пересмотренные рейсы.
3. Проверить один баланс из предыдущего раздела и объяснить разницу между
   количеством топлива и резервом места.
4. Сформулировать вывод своими словами: что улучшилось, что не изменилось
   и что этим экспериментом не доказано. Не писать, что оптимизатор всегда лучше.

Автоматический перенос данных уже выполняет программа. Эти действия нужны
для понимания расчёта и проверки, а не для ручного копирования таблиц.
