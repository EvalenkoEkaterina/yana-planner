# Погодный запрет как событие перепланирования

Обработчик готового события подключён к ядру и CLI. Загрузка метеоданных и
преобразование ветра в интервалы — отдельная работа в модуле `weather.py`.
Этим изменением данные Open-Meteo/ERA5 не скачивались, пороги не калибровались.

## Договор входа

```json
{
  "type": "weather_closure",
  "announced_at_h": 60,
  "closures": [[120, 132]],
  "rule_status": "scenario_assumption",
  "data_kind": "reanalysis",
  "forecast_issued_at": null
}
```

Это пример формата, а не установленное событие из погодного архива.
Интервал `[120,132)` включает начало и исключает конец. Ограничение действует
на движение с грузом и возвращение. Погрузку, приёмку и подготовку он не закрывает.

Преобразователь дополнительно сохраняет источник, набор данных, координаты,
показатель и единицы ветра, порог, правило, время скачивания и соответствие T0
абсолютной дате с часовым поясом. Эти поля сохраняются в снимке события.
Соседние и пересекающиеся запреты объединяются с прежними ограничениями.
Старые запреты не удаляются. Пустой список означает, что новых запретов нет.

Начало каждого нового интервала не раньше объявления. Времена — целые
неотрицательные часы. Перевёрнутые, нулевые и задним числом добавленные интервалы
отклоняются до запуска первоначального решателя. Пока погодное правило должно
быть явно обозначено как `scenario_assumption`.

## История информации

- `synthetic`: искусственный опыт, без подтверждения реальной погоды.
- `reanalysis`: историческое испытание. Доступность будущих условий на момент
  объявления задаётся условно. Это не прогноз и не проверка его точности.
- `forecast`: нужен `forecast_issued_at` с часовым поясом. Нужен абсолютный
  `t0` сценария с поясом либо отдельный IANA `timezone`. Дата выпуска не позже
  `t0 + announced_at_h`. Позже выпущенный прогноз отклоняется.

Для реанализа и синтетики время выпуска прогноза отсутствует или null.
Проверка даты выпуска не доказывает точность, достаточную дальность прогноза
или применимость порога к судну. Время скачивания не заменяет дату выпуска.
В исходном R03 часовой пояс пока не задан: настоящий прогноз нельзя привязать
к его T0 без явного пояса.

## Путь расчёта

1. Проверка события без раскрытия будущих запретов первоначальному решателю.
2. Исходные READY и MILP только на исходных условиях.
3. Фиксация рейсов, начатых включительно к часу объявления.
4. Добавление запретов и пересчёт будущего. Новые погрузки строго позже объявления.
5. Независимая проверка движения, возврата, причалов, груза и сроков.

Если запрет пересекает движение/возврат начатого рейса, результат —
`requires_intervention`. Рейс не переносится в прошлом, его груз не меняется.
Возможность остановить судно в пути или задержать возврат отдельно не
моделируется. Принятый объём и экономия при конфликте неизвестны, а не нулевые.
У методов собственные исходные планы и зафиксированные истории.
Для одинакового префикса можно передать один исходный план в `replan` вручную.

## Воспроизводимый запуск

```sh
yana replan examples/r03.json --event examples/weather-closure.json --deadline 328 --time-limit 2 --out outputs/weather-closure
```

Файл `examples/weather-closure.json` помечен **synthetic**: условные `[120,132)`
и объявление в 60 ч, без загруженной метеорологии. Выдаются JSON, HTML, CSV.
В отчёте карточка погодного события, сравнение до/после и диаграммы.

Экономическая стратегия также работает при перепланировании:

```sh
yana replan examples/r03.json --event examples/weather-closure.json --deadline 328 --strategy cost --cost-terms examples/costs.per-vessel.demo.json --time-limit 2 --out outputs/weather-cost
```

Ставки примера вымышлены. Тот же набор тарифов, заявленный флот и общий горизонт
действуют до и после события. Разность затрат после события показывается только
при допустимых планах с одинаковым принятым объёмом. Приоритет объёма сохраняется.
Экономический режим также работает с прежней задержкой `arrival_delay`.

## API команды

- `apply_event(cfg, event)`: проверенный снимок новых условий.
- `apply_weather_closure(cfg, event)`: применение погодного события.
- `replan(cfg, initial_plan, event, deadline, method="milp", strategy="cost", cost_terms=terms)`:
  продолжение готового плана с фиксацией истории.
- `run_replanning(cfg, event, deadline, strategy="cost", cost_terms=terms)`:
  полный опыт до/после; экономические аргументы необязательны.

Погодные события доступны через JSON/CLI, функции ядра и веб-маршрут
`POST /api/plan`. Контракт и готовые примеры — [frontend-api.md](frontend-api.md).
Форма Аверкиевой v2 также передаёт явное погодное событие через адаптер
пакета. Это ручной ввод готовых интервалов, а не подключённая погодная модель.
Статус: [averkieva-server-integration.md](averkieva-server-integration.md).

Катя делает свой `weather.py` и проверки преобразования. Общие планировщик,
модель и обработчик события ей менять не нужно. Для первого подключения
достаточно JSON события и фрагмента исходных данных, объясняющего интервалы.
Надежда может опираться на этот формат для интерфейса.
