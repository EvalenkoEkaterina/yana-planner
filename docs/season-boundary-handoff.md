# Передача логики конца навигационного сезона

## Что входит в этот коммит

Два независимых модуля: `navigation.py` (CSV, отбор наблюдений, медиана/P20, календарная арифметика) и `season_constraint.py` (перевод календарной границы в существующий `return_cutoff_h`, календарные проверки готовых рейсов). Также добавлены пустой CSV-шаблон и тесты. Страницы, серверные обработчики, алгоритмы, тарифы и зависимости этим коммитом не изменены. Основа ветки — версия интегратора `375430b`.

Это пакет для подключения, а не уже включённая функция сайта. Не нужно переносить из ветки Ушановой коммиты переделки интерфейса `dccd88a` и `13be26b`.

## Методика и данные

Участок: **Усть-Куйга — Нижнеянск**. CSV UTF-8: `year,date,section,event_type,source`. Тип события — `navigation_aids_removed` или `traffic_ended`; типы не смешиваются. Разделители запятая и точка с запятой поддерживаются. Один год/одна дата считаются один раз; противоречащие даты одного года требуют уточнения. Для оценки 2026 года используются только годы до 2026. Пустая история не заменяется вымышленными значениями.

Медиана и P20 вычисляются линейной интерполяцией по позиции `(n−1) × p` в общем високосном календаре месяцев/дней 2000 года, затем переносятся в год оценки. При переносе 29 февраля в невисокосный год используется 28 февраля. Сохраняются n, годы, использованные источники и причины исключений. Менее пяти наблюдений отмечаются как малая выборка; это предупреждение, не статистический критерий достаточности. P20 — ранний осторожный ориентир, не гарантия 80% надёжности.

Ручная дата 30.09.2026 — пользовательское значение с непроверенным источником. Дата без времени означает **00:00 UTC+10 в начале указанного дня**, а не конец дня. Время можно задать явно. Закрытие судоходной обстановки не тождественно фактическому прекращению движения; календарный результат не является разрешением на рейс.

## Минимальный вызов

После проверки входного сценария, но **до** запуска READY/MILP, создать отдельную копию входов и вызвать:

```python
from copy import deepcopy
from yana_planner.season_constraint import (
    apply_season_constraint, attach_season_trip_checks,
)

cfg = deepcopy(validated_scenario)
spec = {
    "section": "Усть-Куйга — Нижнеянск",
    "year": "2026",
    "start": "2026-09-29T09:00:00+10:00",
    "reserve_h": "3",
    "mode": "manual",  # либо p20 / median при наличии csv_text
    "manual_boundary": "2026-09-30",
    "manual_source": "Пользовательское значение; источник не проверен",
    "event_type": "navigation_aids_removed",
    "csv_text": "",
}
deadline = apply_season_constraint(cfg, requested_deadline, spec)
# Дальше обычный вызов compare или run_replanning с существующими
# strategy, cost_terms, event и прочими аргументами интегратора.
# После расчёта:
attach_season_trip_checks(cfg, result)
```

Даты и запас в примере вызова — условные входы демонстрации, не сведения о реальном рейсе. В интерфейсе начало и запас должен явно ввести пользователь.

Перед вызовом интегратор обязан проверить, что фактически выбранный маршрут относится к данному участку. `spec.section` передаётся из проверенного сервером контекста маршрута, а не назначается всем путям по умолчанию. Модуль отклоняет другой текст участка, но сам не проверяет граф. Для другого участка нужна отдельная история и отдельное согласование. Многополучательная кампания автоматически этой функцией не поддерживается.

## Что изменяется в расчёте

Функция изменяет только переданную копию cfg: сужает `return_cutoff_h` и записывает `season_assessment`. ID и приоритеты сценария сохраняются. Возвращаемый deadline — меньший из прежнего срока приёмки и нового срока возврата. Календарная граница переводится в часы от start, из неё вычитается резерв, дробные часы округляются вниз. Прежний более строгий горизонт возврата не расширяется. Суда, партии, длительности, тарифы и оплачиваемый горизонт не меняются.

Текущие кандидаты и независимая проверка уже контролируют return_cutoff_h. Дополнительная погодная модель и новые функции оптимизатора не нужны. Момент начала в плане — **начало погрузки**: последний допустимый старт включает погрузку, движение туда, выгрузку и возврат. Подготовка после возвращения сохраняет прежний смысл доступности для следующего рейса.

Если `deadline == 0`, положительный рейс не помещается. В прямом вызове compare это проверено: ноль доставленных тонн и полная недопоставка. В API `calculate_request` и импорте пакета сейчас требуется deadline >= 1: нельзя передавать 0 туда без отдельной обработки. Нужно показать «Сезонная граница уже достигнута» и не запускать такой запрос либо явно согласовать отдельный нулевой результат. Не подменять 0 на 1.

Если событие задержки/погоды объявлено после нового эффективного срока приёмки, нельзя незаметно сдвигать событие или отбрасывать историю. Нужна отдельная обработка сообщения пользователю. Граница сезона здесь известна перед новым запуском; изменение границы во время уже начатого рейса не реализовано этим пакетом.

Для схемы all_available_time сохранять прежний `cost_terms.horizon_h`: уменьшение допустимого времени возвращения не означает сокращения оплаченного договора. Сезонную границу нельзя молча превратить в меньший платёж.

В актуальной модели возможна погрузка со скоростью `load_rate_tph`. Проверка готового рейса использует разность проверенных `return_h − start_h`, поэтому учитывает фактическую длительность погрузки выбранной партии, не предполагая постоянный load_h.

## Как показать в интерфейсе

Перед запуском: начало расчёта, год, запас, тип события, CSV и выбор manual/p20/median. Историю можно предварительно показать через `read_history` + `estimate_history`. Не обещать приблизительную дату без фактической истории.

После расчёта: `cfg['season_assessment']` содержит границу, основание, медиану/P20, n, годы, источники, исходный и эффективный срок возврата. После attach появляются `trip_checks['READY']` и `trip_checks['MILP']` с календарными возвращениями, запасом, последним допустимым началом погрузки и fits. При перепланировании таблица относится к итоговым планам. Пустая таблица рейсов не подтверждает выполнение поставки. Снимок cfg нужно сохранить в существующем отчёте/JSON вместе с параметрами расчёта; не пересчитывать историческую оценку при открытии сохранённого результата.

## Проверки

```sh
PYTHONPATH=src python -m unittest discover -s tests -p test_navigation.py -v
PYTHONPATH=src python -m unittest discover -s tests -p test_season_handoff.py -v
```

Проверяются календарные границы, переход между годами, високосные даты, исключение текущего года, исходные READY/MILP, равенство возвращения границе с запасом, рейс вне сезона, погрузка по производительности, экономическая стратегия и неизменность оплачиваемого горизонта, задержка поступления. Данные тестов синтетические. Реальная многолетняя таблица пока не предоставлена.
