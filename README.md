# Yana Planner

## Материалы для экспертов

[Паспорт, гипотезы, код, данные и все артефакты](https://github.com/EvalenkoEkaterina/yana-planner/releases/tag/mai3-submission-2026-11-10). В выпуске доступны два документа и полный архив с отчётами.

[Проверенная версия кода, к которой относятся результаты](https://github.com/EvalenkoEkaterina/yana-planner/tree/integration/pr2-economics). Основная ветка может отличаться от зафиксированной версии выпуска.

Исследовательский Python-проект для планирования доставки нефтяного котельного топлива Нижнеянск - Усть-Куйга. Выбирает суда, время погрузки и партии, проверяет исполнение и перестраивает будущие отправления после задержки поступления.

Публичный репозиторий команды: [EvalenkoEkaterina/yana-planner](https://github.com/EvalenkoEkaterina/yana-planner). Просмотр кода и материалов доступен без приглашения. Для работы с копией:

```sh
git clone https://github.com/EvalenkoEkaterina/yana-planner.git
cd yana-planner
```

Задания и владельцы модулей указаны в [плане команды](docs/team-work.md). Изменения готовятся в отдельных ветках и передаются через Pull Request.

Версия 0.1.0 работает на сценарных данных. Ориентир задания 1650 т взят из закупки. Операционные числа в примерах заданы условно. Реальная доступность судов, грузовая шкала и возможность приёмки не подтверждены. Программа не подтверждает безопасность реального рейса и не объявляет расчёт фактической экономией.

## Быстрый запуск

Python 3.12+. В папке репозитория:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install --no-deps -e .
python -m unittest discover -s tests -v
```

В Windows активация: `.venv\Scripts\activate`.

Контрольное сравнение:

```sh
yana plan examples/r03.json --deadline 328 --reference examples/r03.reference.json --out outputs/static
```

Откройте `outputs/static/report.html`: рядом будут результаты JSON, таблица CSV, расписание и событийный баланс. Флаг `--reference` использует ранее найденный допустимый план как кандидата, заново проверяя его. Для поиска с нуля уберите этот флаг. При ограничении времени последнее время приёмки может различаться - смотрите статусы решателя.

Проверенный контроль R03/328: оба метода принимают 1650 т, READY делает 6 рейсов с последней приёмкой в 276 ч, известный MILP-план - 5 рейсов с последней приёмкой в 224 ч. Средняя приёмка по тоннам у этого MILP-плана позже: это сохранённый компромисс разных целей.

## Перепланирование

```sh
yana replan examples/r03.json --event examples/arrival_delay.json --deadline 328 --reference examples/r03.reference.json --out outputs/replanning
```

Первоначальный план получает поступления в 0/120 ч. Только на 60-м часу раскрывается перенос второго поступления на 168 ч. Уже начатые рейсы каждого метода фиксируются. Для новых отправлений допускается время строго после момента наблюдения. Модель не переигрывает прошлое и не возвращает погруженное топливо в источник.

Поддерживается один тип события `arrival_delay` и один цикл обновления. Многократные события и ошибки прогноза не реализованы. Если новые ограничения делают начатый рейс недопустимым, планировщик требует вмешательства, а не подменяет его историю.

## Входы из Excel

Единственный входной лист - `Входы_модели`. Два явных профиля:

```sh
yana import-excel tests/fixtures/team-r03.xlsx --profile team-r03 --sim-only --out outputs/from_excel.json
yana plan outputs/from_excel.json --out outputs/excel_run
```

- `team-r03`: стартовая книга команды с данными R03 в колонке C и таблицами судов/поступлений на том же листе.
- `resource-v1`: исправленная книга SIM-BASE с активными значениями в K, диапазонами I04/I05 и переключателем L35. Неизвестные срок и возврат задаются явно `--deadline 328 --return-cutoff 492`.

`--sim-only` явно задаёт учебные допущения о проходе/приёмке. BASE не конвертируется в подтверждённый сценарий автоматически. Неизвестные параметры не заполняются нулями. Импорт читает книгу, не изменяя её. Произвольные иные макеты XLSX не поддерживаются.

## Полная серия и отдельная проверка

```sh
yana benchmark examples/v2_suite.json --out outputs/benchmark
yana validate examples/r03.json examples/r03.reference.json --deadline 328 --out outputs/validation.json
```

Серия содержит 72 пары, включая 8 повторных контрольных пар (64 разных сочетания входов и срока). Статусы и разрывы MILP сохраняются. Контрольные расписания в тестах - результаты предыдущего прототипа, не исторические перевозки.

## Экономика

```sh
yana cost examples/r03.json outputs/static/results.json --deadline 328 --terms examples/costs.template.json --out outputs/costs.json
```

Шаблон ставок намеренно пуст. Команда выбирает и обосновывает сценарные ставки. Поддержана одна явная схема: отдельные расходы рейса + активные судно·ч + оплата остального доступного времени на общем горизонте `all_available_time`. Состав ставок должен исключать двойной счёт. Сравнение расходов разрешено при одинаковом принятом объёме; реальная экономия всегда остаётся неизвестной. Ставки НМЦ не прибавляются к этой модели как себестоимость.

```text

```

## Что учитывает модель

- Источник списывается при начале погрузки, а не при отправлении после неё.
- Ёмкость резервируется при прибытии и остаётся занятой после выгрузки.
- Место освобождается только явно подтверждённым в сценарии отбором; нельзя вывести больше уже принятого топлива.
- Проверяется весь оборот, доступность судна, один причал погрузки и один причал приёмки.
- Предел партии проверяется на всём гружёном плече, остановка - на гружёном ходе и возврате.
- Приёмка и возврат имеют разные сроки. Стартовая сетка - целые часы, партия - целые тонны. Иные разрешения явно отклоняются.

Прогноз уровней/погоды не обучен. Нет калиброванной зависимости «уровень - глубина - осадка - партия». Длительности операций фиксированы в пределах сценария; стоянки внутри плеча не моделируются. Это ограничения текущего метода, а не отсутствующие поля, которые можно незаметно считать нулём.

## Сайт и история

После установки зависимостей по инструкции выше:

```sh
python -m flask --app yana_planner.web:create_app run --host 127.0.0.1 --port 5001
```

Откройте http://127.0.0.1:5001. Форма заполнена примером R03. Можно изменить
цель, срок приёмки и возврата, начальный запас и вместимость получателя.
Добавляйте и удаляйте суда (1–6), задавайте каждому свою вместимость,
доступность и длительности операций. В таблице поступлений (1–12) задаются
час и объём пополнения запаса отправителя. Вместимость 400 т не зафиксирована:
для каждого судна действует введённое значение.

В режиме «С задержкой топлива» выберите номер поступления, момент сообщения
и новое время поступления. Событие должно относиться к ещё не поступившей
партии и переносить её на более поздний момент. Начатые рейсы сохраняются.
В режиме без задержки её поля скрыты и не влияют на расчёт. Под формой
показывается сводка выбранных условий. Ошибки сохраняют введённые значения.
Ссылка «восстановите пример» возвращает исходный R03.

Результат и полный HTML-отчёт содержат таблицу введённых судов, поступления
и событие. Пример для проверки нового ввода: цель и вместимость получателя
600 т, одно судно на 600 т с доступностью 0 ч, операциями 2/4/2/4/2 ч,
одно поступление 600 т в 0 ч, приёмка до 30 ч, возврат до 50 ч. READY и MILP
принимают 600 т за один рейс.

SQLite создаётся автоматически в `instance/runs.sqlite3`, путь можно изменить
переменной `YANA_DATABASE`. История сохраняется после перезапуска. Результат,
входы, событие, кандидат reference, настройки и отпечаток исходного кода
сохраняются вместе. Просмотр, отчёт и скачивание не запускают решатель.
Статус `completed` означает завершённый допустимый расчёт, а доказательство
оптимальности показано отдельно для каждого сравнения. Невыполненная цель
показывается отдельным предупреждением.

Допустимый срок сайта — целые 1–492 ч, максимум ограничен конфигурацией
`MAX_DEADLINE_H` и выбранным сроком возврата. Все времена в форме ограничены
492 ч, объёмы — 1 000 000 т. Малый срок может давать недопоставку.
Форма предлагает 2, 10 или 30 секунд на этап MILP, по умолчанию выбраны 10 с.
Для вызовов без выбора бюджета действует конфигурация сервера (2 с).
Увеличение бюджета может улучшить план и позволить доказать оптимальность,
но не гарантирует ни улучшения, ни подтверждения оптимума на любых данных.
Выбранный лимит сохраняется в исходных условиях и выводится в отчёте.
До трёх этапов на вызов;
перепланирование вызывает MILP повторно, поэтому это не лимит полного запроса.
Демонстрационный сервер работает локально, без регистрации и очередей.

с `--reference examples/r03.reference.json`:

| Расчёт / метод | Принято, т | Осталось, т | Рейсов | Завершение приёмки, ч |
|---|---:|---:|---:|---:|
| R03 READY | 1650 | 0 | 6 | 276 |

| Задержка READY | 1650 | 0 | 6 | 284 |

Все четыре расписания допустимы по независимому валидатору. В этом запуске

Числа показывают результат учебной модели, а не фактический эффект перевозок.

Входы: `examples/r03.json`, `examples/arrival_delay.json`, reference в той же папке.
Команды воспроизведения приведены в разделах быстрого запуска и перепланирования.

## Проблема, адресат и кейс А3

Рассматриваем конкретный российский маршрут Нижнеянск — Усть-Куйга.
Поступление топлива частями, различия судов и ограниченный срок приёмки
требуют согласовать загрузку, перевозку, приёмку и возврат. Предложение
адресовано организатору завоза, логисту перевозчика и принимающей стороне;
полномочия конкретного заказчика команда не устанавливала.
Оптимизатор согласует решения на всём горизонте, вместо последовательного
назначения первого доступного рейса READY. READY — учебная база сравнения,
его соответствие практике перевозчика не заявляется.

Происхождение сведений и собранные командой ссылки приведены в
[реестре источников](docs/data-provenance.md). Ориентир 1650 т относится
к плановым требованиям закупки; суда, времена и задержка — допущения.
Исходные PDF кейса А3 и главный документ ТЗ в этой копии отсутствуют:
соответствие проверено по предоставленному тексту требований, а ссылки команды
не являются новой независимой проверкой первичных документов.
Сопоставимость обеспечивается общими входами и сроком; после события каждый
метод сохраняет собственные начатые рейсы. При разных объёмах отчёт явно
ограничивает сравнение. Денежный эффект без ставок не рассчитывается.

## Подготовка защиты

[Сценарий показа за 4 минуты](docs/demo-guide.md): порядок демонстрации,
объяснение диаграмм и ответы об ограничениях. В результатах и HTML-отчётах
показаны этапы рейсов по судам; начатые рейсы при задержке выделены рамкой.
Численные разницы формируются общей функцией только при равном объёме.
Запасные самодостаточные отчёты — `demos/static/report.html` и
`demos/replanning/report.html`; открываются без сервера и интернета.

На основной странице результатов также показано среднее время приёмки,
взвешенное по тоннам, с объяснением компромисса целей. Блок «Что изменилось
после задержки» считает изменения отдельно для каждого метода (после − до).
Все диаграммы одного расчёта используют общую шкалу; номера и тоннаж рейсов
подписаны на полосах. На широком экране методы расположены рядом.

### Напряжённый срок: устранение недопоставки в учебном сценарии

При задержке R03 и сроке 280 ч проверенный расчёт дал READY 1625 т,
MILP 1650 т при пяти рейсах у каждого. У MILP недопоставка 0 т против 25 т
у READY. Здесь сравниваем выполнение цели, а не скорость доставки разных
объёмов. Входы и математическая постановка прежние, меняется только срок.
Результаты и запасной отчёт: `demos/deadline280/`; команды в
[инструкции демонстрации](docs/demo-guide.md).
