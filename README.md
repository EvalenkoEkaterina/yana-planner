# Yana Planner

## Материалы для экспертов

[Паспорт, гипотезы, код, данные и все артефакты](https://github.com/EvalenkoEkaterina/yana-planner/releases/tag/mai3-submission-2026-11-10). В выпуске доступны два документа и полный архив с отчётами.

[Проверенная версия кода, к которой относятся результаты](https://github.com/EvalenkoEkaterina/yana-planner/tree/a28aba83b43653ddf4eb9fd15deb8c8c0e827570). Основная ветка может отличаться от зафиксированной версии выпуска.

Исследовательский Python-проект для планирования доставки нефтяного котельного топлива Нижнеянск — Усть-Куйга. Выбирает суда, время погрузки и партии, проверяет исполнение и перестраивает будущие отправления после задержки поступления.

Публичный репозиторий команды: [EvalenkoEkaterina/yana-planner](https://github.com/EvalenkoEkaterina/yana-planner). Просмотр кода и материалов доступен без приглашения. Для работы с копией:

```sh
git clone https://github.com/EvalenkoEkaterina/yana-planner.git
cd yana-planner
```

Задания и владельцы модулей указаны в [плане команды](docs/team-work.md). Изменения готовятся в отдельных ветках и передаются через Pull Request.

**Версия 0.1.0 работает на сценарных данных.** Ориентир задания 1650 т взят из закупки. Операционные числа в примерах заданы условно. Реальная доступность судов, грузовая шкала и возможность приёмки не подтверждены. Программа не подтверждает безопасность реального рейса и не объявляет расчёт фактической экономией.

## Быстрый запуск

Python 3.12+. В папке репозитория:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install --no-deps -e .
python -m unittest discover -s tests -v
```

В Windows активация: `.venv\Scripts\activate`.

Контрольное сравнение:

```sh
yana plan examples/r03.json --deadline 328 --reference examples/r03.reference.json --out outputs/static
```

Откройте `outputs/static/report.html`: рядом будут результаты JSON, таблица CSV, расписание и событийный баланс. Флаг `--reference` использует ранее найденный допустимый план как кандидата, заново проверяя его. Для поиска с нуля уберите этот флаг. При ограничении времени последнее время приёмки может различаться — смотрите статусы решателя.

Проверенный контроль R03/328: оба метода принимают 1650 т, READY делает 6 рейсов с последней приёмкой в 276 ч, известный MILP-план — 5 рейсов с последней приёмкой в 224 ч. Средняя приёмка по тоннам у этого MILP-плана позже: это сохранённый компромисс разных целей.

## Перепланирование

```sh
yana replan examples/r03.json --event examples/arrival_delay.json --deadline 328 --reference examples/r03.reference.json --out outputs/replanning
```

Первоначальный план получает поступления в 0/120 ч. Только на 60-м часу раскрывается перенос второго поступления на 168 ч. Уже начатые рейсы каждого метода фиксируются. Для новых отправлений допускается время строго после момента наблюдения. Модель не переигрывает прошлое и не возвращает погруженное топливо в источник.

Поддерживаются два типа сообщения: `arrival_delay` и `vessel_unavailable`,
один цикл обновления за запуск. Многократные события и ошибки прогноза не
реализованы. Если новое ограничение конфликтует с начатым рейсом, возвращается
`requires_intervention`, а история сохраняется.

Отдельный опыт A2: в час 60 сообщают о недоступности SIM-A в [120,200) ч.
Поступления остаются в 0/120 ч; задержка топлива из A1 сюда не добавляется.

```sh
yana replan examples/r03.json --event examples/vessel_unavailable.json --deadline 328 --reference examples/r03.reference.json --time-limit 10 --out outputs/vessel_unavailable
```

В проверенном запуске READY принял 1650 т за 6 рейсов с последней приёмкой
в 280 ч; MILP — те же 1650 т за 5 рейсов, последняя приёмка в 264 ч.
Полный оборот судна, включая подготовку, должен обходить интервал недоступности.
Это сценарный эксперимент, не сведения о реальном ремонте судна.
[Формат события, проверки и результат](docs/vessel-unavailability.md).

## Сводка для сравнения и защиты

```sh
yana summarize outputs/static/results.json --out outputs/static/summary.json
yana summarize outputs/replanning/results.json --out outputs/replanning/summary.json
```

Сводка `experiments.py` читает результаты независимой проверки: одну строку для
обычного сравнения или две строки «до/после» для перепланирования. При разных
объёмах она не объявляет уменьшение рейсов или времени улучшением. Неизвестные
и недопустимые показатели остаются `null`. Компромисс учитывает и среднюю приёмку
по тоннам: более ранняя последняя партия не означает более раннюю среднюю тонну.
Сводка не заменяет проверку расписания и не доказывает оптимальность или реальную
экономию. [Первый шаг интегратора](docs/integrator-first-step.md).

## Серия сроков доставки

```sh
yana sweep-deadlines examples/r03.json --event examples/arrival_delay.json --start 240 --stop 336 --step 8 --reference examples/r03.reference.json --time-limit 3 --out outputs/deadline_sweep
```

Серия сохраняет все выбранные точки, отдельные расписания, статусы решателя,
сводку CSV/JSON и `report.html`. До первого расчёта сохраняется `protocol.json`
с входами, сообщением, сеткой и лимитом времени на каждую стадию решателя.
Времена и рейсы как улучшения сравниваются только при равном объёме.

Для графиков установите необязательное дополнение `python -m pip install -e '.[plots]'`
и добавьте к команде `--plot`. Получатся PNG и SVG. Основная программа и тесты
работают без Matplotlib.

В R03 после задержки на сетке 240–336 ч с шагом 8 ч получены: 240–264 ч —
1225/1625 т, 272–280 ч — 1625/1650 т, 288–336 ч — 1650/1650 т.
Это проверенные точки сетки, а не все промежуточные сроки и не вероятность
успеха на реальных рейсах. [Методика и результаты](docs/deadline-sweep.md).

## Совместимость с работой из PR №1

Поддерживается файл участницы `examples/vessel_unavailability.json`:
`type=vessel_unavailability` и `interval=[120,200]`. Он преобразуется в общий
формат `vessel_unavailable` с `from_h` / `to_h`. Оригинал сообщения сохраняется
в `source_event`; противоречивые границы отклоняются.

Функции участницы доступны в `yana_planner.online`, используют общий движок
и возвращают как общие поля результата, так и прежние имена для совместимости.
Сохранённые результаты её исходной версии теперь тоже читаются сводкой:

```sh
yana report outputs_online/unavailability_experiment.json --out outputs/pr1_saved
yana summarize outputs/pr1_saved/results.json --out outputs/pr1_saved/summary.json
```

`report` создаёт отчёт, таблицы и `summary.json`. Исходный файл не меняется.
Адаптация формата не заменяет независимую проверку расписания.
[Интеграция, контракт и проверенные цепочки](docs/pr1-integration.md).

## Входы из Excel

Единственный входной лист — `Входы_модели`. Два явных профиля:

```sh
yana import-excel tests/fixtures/team-r03.xlsx --profile team-r03 --sim-only --out outputs/from_excel.json
yana plan outputs/from_excel.json --out outputs/excel_run
```

- `team-r03`: стартовая книга команды с данными R03 в колонке C и таблицами судов/поступлений на том же листе.
- `resource-v1`: исправленная книга SIM-BASE с активными значениями в K, диапазонами I04/I05 и переключателем L35. Неизвестные срок и возврат задаются явно `--deadline 328 --return-cutoff 492`.

`--sim-only` явно задаёт учебные допущения о проходе/приёмке. BASE не конвертируется в подтверждённый сценарий автоматически. Неизвестные параметры не заполняются нулями. Импорт читает книгу, не изменяя её. Произвольные иные макеты XLSX не поддерживаются.

## Полная серия и отдельная проверка

```sh
yana benchmark examples/v2_suite.json --out outputs/benchmark
yana validate examples/r03.json examples/r03.reference.json --deadline 328 --out outputs/validation.json
```

Серия содержит 72 пары, включая 8 повторных контрольных пар (64 разных сочетания входов и срока). Статусы и разрывы MILP сохраняются. Контрольные расписания в тестах — результаты предыдущего прототипа, не исторические перевозки.

## Экономика

Модуль экономической оценки рассчитывает условные расходы по уже построенному и независимо проверенному расписанию. Количество рейсов, занятые судно·часы и оплачиваемое время ожидания извлекаются из расписания автоматически.

Поддерживаются две схемы учёта ожидания:

- `inter_voyage_gaps` — оплачиваются только промежутки между завершением полного оборота судна и началом его следующего рейса.
- `all_available_time` — оплачивается всё неактивное время от `available_h` до общего горизонта. Это сценарное условие оплаты, включая совпадение с недоступностью судна, а не подтверждённый договор.

Расчёт включает три компонента:

- отдельные расходы на один рейс;
- расходы на активные судно·часы;
- расходы на оплачиваемое время ожидания.

Общая формула:

`C = N × F + H_active × R + H_wait × P`

где `N` — число рейсов, `F` — ставка на рейс, `H_active` — занятые судно·часы, `R` — ставка активного часа, `H_wait` — оплачиваемые часы ожидания, `P` — ставка часа ожидания.

Шаблон `examples/costs.template.json` намеренно содержит неизвестные ставки как `null`. Команда должна выбрать и обосновать сценарные значения. Неизвестные расходы не приравниваются к нулю.

Обычный расчёт:

```bash
yana cost examples/r03.json outputs/static/results.json --deadline 328 --terms examples/costs.template.json --out outputs/costs.json
```

После перепланирования команды экономики используют `updated_input` и
повторно проверяют допустимость обоих планов. По умолчанию выбирается фаза
после события; `--phase before` позволяет оценить исходную фазу. Поддержаны
сохранённые результаты PR №1. Разные тоннажи и недопустимые статусы отклоняются.

### Анализ чувствительности

Команда `yana sensitivity` сравнивает экономический результат расписаний при разных сочетаниях сценарных ставок. Анализ позволяет проверить, как меняется преимущество расписания при изменении стоимости рейса, активного времени и ожидания, а также рассчитать динамическую точку безубыточности.

Пример:

```bash
yana sensitivity examples/r03.json outputs/static/results.json --deadline 328 --horizon 328 --out outputs/sensitivity.json
```

Результаты формируются отдельно для каждой схемы учёта ожидания. Точка безубыточности зависит от фактических различий между расписаниями и выбранных ставок; она не задаётся заранее фиксированным числом.

**Ограничения:** все ставки и рассчитанные расходы являются сценарными, а не подтверждёнными фактическими затратами. Сравнение расходов допускается только при одинаковом принятом объёме. Ставки НМЦ закупки не используются как себестоимость перевозки. Более дешёвое расписание не обязательно улучшает сроки средней приёмки или другие показатели. Реальная экономия остаётся неизвестной.

## Структура

```text
src/yana_planner/
  domain.py         Проверка входного контракта и неизвестных значений
  validation.py     Независимая реконструкция рейсов и балансов
  planning.py       READY и целочисленный планировщик
  replanning.py     Новая информация и фиксация начатых рейсов
  sensitivity.py   Анализ чувствительности и точки безубыточности
  economics.py      Отдельная условная модель расходов
  experiments.py    Сводка проверенных результатов и компромиссов
  excel_import.py   Чтение листа Входы_модели
  io.py             Выгрузки JSON, CSV и HTML
  cli.py            Команды запуска
tests/              Механика, ошибки, границы, перепланирование, экономика, чувствительность, регрессии v2
examples/           Сценарии, событие задержки, шаблон затрат
docs/               Формулы, допущения, задачи команды, источники
```

## Что учитывает модель

- Источник списывается при начале погрузки, а не при отправлении после неё.
- Ёмкость резервируется при прибытии и остаётся занятой после выгрузки.
- Место освобождается только явно подтверждённым в сценарии отбором; нельзя вывести больше уже принятого топлива.
- Проверяется весь оборот, доступность судна, один причал погрузки и один причал приёмки.
- Предел партии проверяется на всём гружёном плече, остановка — на гружёном ходе и возврате.
- Приёмка и возврат имеют разные сроки. Стартовая сетка — целые часы, партия — целые тонны. Иные разрешения явно отклоняются.

Прогноз уровней/погоды не обучен. Нет калиброванной зависимости «уровень — глубина — осадка — партия». Длительности операций фиксированы в пределах сценария; стоянки внутри плеча не моделируются. Это ограничения текущего метода, а не отсутствующие поля, которые можно незаметно считать нулём.

Самостоятельный вклад участников следует отмечать по изменениям и проверкам, которые они действительно выполнили. [Задачи команды](docs/team-work.md), [математика](docs/model.md), [источники](docs/data-provenance.md).


Исправления экономики PR №2 и результаты проверки:
[интеграция экономики](docs/pr2-economics-integration.md). Отрицательный корень
уравнения не выдаётся за допустимый тариф; отсутствие горизонта даёт явный
статус нехватки входов. Все денежные значения остаются сценарными.
