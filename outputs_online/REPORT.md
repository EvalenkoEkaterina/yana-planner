## Сценарий

- Маршрут: Нижнеянск — Усть-Куйга.
- Груз по текущей версии общей программы: нефтяное котельное топливо.
- Задание: 1 650 т; срок приёмки: 328 ч; срок возврата: 492 ч.
- Событие: на 60-м часу объявлено, что SIM-A недоступно в интервале [120, 200) ч.
- Недоступность хранится отдельно в `vessels[].unavailable_intervals`; исходное `available_h` не меняется.
- Рейсы, начатые к 60-му часу, сохраняются. Новые рейсы начинаются строго после момента наблюдения.
- Проверяется полный оборот `[start_h, ready_h)`, включая погрузку, гружёный ход, выгрузку, возврат и подготовку.

Все эксплуатационные параметры — сценарные, не подтверждение реальной возможности рейса.

## Результаты

| Метод | До события: принято / рейсы / последняя приёмка | После события: принято / недопоставка / рейсы / последняя приёмка | Средневзвешенная приёмка после | Занятость после | Начатых рейсов сохранено | Проверка |
|---|---:|---:|---:|---:|---:|---|
| READY | 1650 т / 6 / 276 ч | 1650 т / 0 т / 6 / 280 ч | 159,76 ч | 468 судно·ч | 2 | valid_simulation |
| MILP | 1650 т / 5 / 224 ч | 1650 т / 0 т / 5 / 264 ч | 157,92 ч | 404 судно·ч | 2 | valid_simulation |

До события средневзвешенное время приёмки, пересчитанное независимой проверкой из контрольных рейсов: READY 136,70 ч; MILP 146,42 ч. Не следует трактовать меньшее последнее время как автоматическое улучшение всех показателей.

После события оба метода доставляют 1 650 т к сроку. READY сохраняет 6 рейсов и завершает на 4 ч позже исходного READY. MILP сохраняет 5 рейсов, но последняя приёмка сдвигается на 40 ч относительно исходного MILP. Это результат одного сценария, не гарантия преимущества метода.

## Что сделано

1. В `domain.py` добавлен контракт временных интервалов недоступности судна отдельно от первоначального `available_h`.
2. В `planning.py` генератор кандидатов исключает рейсы, полный оборот которых пересекает временную недоступность.
3. В `validation.py` независимая проверка сама восстанавливает `ready_h` и проверяет пересечение `[start_h, ready_h)` с каждым интервалом недоступности.
4. В `online.py` добавлены применение события и перепланирование READY/MILP с фиксацией начатых рейсов.
5. Добавлен пример `examples/vessel_unavailability.json`.
6. Добавлены тесты границ, одноступенчатого пересечения, конфликта уже начатого рейса, а также регрессии пересечений погрузки и выгрузки.

## Почему так

Интервал недоступности — отдельное временное ограничение ресурса. Его нельзя записывать в `available_h`, поскольку это изменило бы первоначальную дату доступности и исказило бы историю. Пересечение проверяется на полном цикле судна, а не только на движении. Планировщик использует ограничение при генерации кандидатов; валидатор независимо повторяет расчёт по исходным длительностям судна.

## Проверка

Команда запуска из корня репозитория:

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
```

Результат: **70 тестов пройдены**. Включены существующие тесты проекта и новые тесты `tests/test_online.py`. MILP решается через SciPy/HiGHS; для обновлённого сценария все три стадии MILP завершились со статусом optimal.

## Что пока не реализовано / ограничения

- Событие недоступности сейчас поддерживается отдельным типом. Слияние нескольких одновременно объявленных событий с задержкой поставки в единый последовательный поток событий требует отдельного интеграционного шага.
- В исходной версии вызов был доступен только через Python API. В интегрированной версии этот формат события принимает общий CLI; старый Python API сохранён.
- Работа опубликована в [PR №1](https://github.com/EvalenkoEkaterina/yana-planner/pull/1); первоначальная версия ZIP и численные результаты сохранены в истории.
- Все входы остаются сценарными; реальная допустимость требует подтверждения.
- Экономика после перепланирования здесь не пересчитывалась.
